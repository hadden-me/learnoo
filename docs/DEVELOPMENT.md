# Development

Two programs live in this repository and stay separate:

- `cmd/server`: the application server: PostgreSQL, migrations, accounts, sessions and login (LRN-005), server-side permission checks, operator commands (LRN-013), the Studio API for lesson drafts and media (LRN-006), review and publication (LRN-007), withdrawal, unpublication and restoration (LRN-009), and the server-rendered student reader with invited student accounts (LRN-008).
- `cmd/renderer`: the loopback-only renderer experiment (LRN-004), below. It has no accounts or database and does not share code paths with the server.

## Application server

No secrets have defaults or belong in the repository. Put local values in your shell or an ignored `.env` file.

### Local PostgreSQL

Option A, Docker Compose (loopback-only, trust authentication, no stored password):

```sh
docker compose up -d postgres
export LEARNOO_DATABASE_URL='postgres://learnoo@127.0.0.1:5432/learnoo?sslmode=disable'
export LEARNOO_TEST_DATABASE_URL='postgres://learnoo@127.0.0.1:5432/learnoo_test?sslmode=disable'
```

`scripts/dev-db-init.sql` creates `learnoo_test` when the volume is first created. `docker compose down -v` deletes all local data.

Option B, an existing local PostgreSQL 16 (for example Homebrew `postgresql@16`): create a `learnoo` role and the `learnoo` and `learnoo_test` databases owned by it, then export the same variables with your own connection details. Tests need permission to create schemas in the test database.

### Migrate, create an account, start

```sh
go run ./cmd/server migrate           # apply pending migrations; safe to repeat
go run ./cmd/server migrate -check    # exit non-zero if anything is pending or was edited
read -rs PW && printf '%s\n' "$PW" | go run ./cmd/server create-user -email you@example.test -name 'Your Name'; unset PW
LEARNOO_MEDIA_DIR="$HOME/.local/share/learnoo/media" go run ./cmd/server serve   # http://127.0.0.1:8090
```

`serve` refuses to start while migrations are pending or the applied history differs from the files. `create-user` reads the password (12 to 1024 characters) from stdin so it never appears in shell history or process lists; it creates an account with no permissions (a Student) and is not public registration.

### Operator commands: first administrator, permissions and account status

These commands act as the trusted local operator: anyone who can run them against the database is trusted ([DECISIONS.md](DECISIONS.md#role-administration-cli-lrn-013)). Changes are audited with no actor and the self-asserted `<os user>@<hostname>` label of the machine running the command. There is no HTTP equivalent. Every command refuses to run while migrations are pending, validates its arguments before changing anything, and exits non-zero with a message on any error. Secrets are never command-line arguments: passwords are read from stdin.

Bootstrap the first administrator on a new database (account plus `administrator`, `publisher`, `author`, each audited, in one transaction). It is refused while any active administrator exists, including when two runs race:

```sh
read -rs PW && printf '%s\n' "$PW" | go run ./cmd/server bootstrap-admin -email admin@example.test -name 'Admin Name'; unset PW
```

`bootstrap-admin` always creates a new account; if the email is already registered it is refused and nothing changes. To make an existing account the first administrator, grant `administrator`, `publisher` and `author` to it with `grant` (below).

Grant or revoke a global permission (`author`, `publisher`, `administrator`) by email, or `reviewer` for one subject by its `subjects.code` (trimmed and lower-cased, like emails; subjects are added with `add-subject`, below, and none are seeded):

```sh
go run ./cmd/server grant  -email teacher@example.test -permission author
go run ./cmd/server grant  -email teacher@example.test -permission reviewer -subject math
go run ./cmd/server revoke -email teacher@example.test -permission reviewer -subject math
go run ./cmd/server revoke -email teacher@example.test -permission publisher
```

Each effective change writes one `permission_audit` row in the same transaction. Repeating a grant or revoke prints `no change: … already holds …` or `no change: … does not hold …`, exits 0 and writes no audit row. Rejected: an unknown email, permission or subject code, `reviewer` without `-subject`, and a global permission with `-subject`. Revoking `administrator` from the last active administrator (holds `administrator`, account not disabled) is refused; grant it to someone else first.

Disable or re-enable an account by email:

```sh
go run ./cmd/server disable-user -email teacher@example.test
go run ./cmd/server enable-user  -email teacher@example.test
```

Disabling sets `users.disabled_at` and deletes the account's sessions in one transaction; the account can no longer sign in (login answers `invalid_credentials`, as for a wrong password) and holds no effective permissions, but its grants stay stored and apply again once it is enabled. Enabling also deletes any sessions, so the account starts signed out. Each effective change writes one `account_status_audit` row with the operator label; repeating a command prints `no change: … is already disabled` or `… already enabled`, exits 0 and writes no audit row. Disabling the last active administrator is refused; grant `administrator` to another active account first.

Show a user's status, stored permissions, reviewer subjects, permission audit and account status audit history, with the operator label or user id of each change (read-only):

```sh
go run ./cmd/server show-user -email teacher@example.test
```

### Provisioning teachers and the catalogue

The supported M1 path for teachers is operator-provisioned accounts; invitation flows for teachers are LRN-016 (M2). Add the subjects and chapters the pilot needs, then create each teacher and grant what they do:

```sh
go run ./cmd/server add-subject -code maths
go run ./cmd/server add-chapter -subject maths -code complexes
go run ./cmd/server set-subject-name -code maths -fr 'Mathématiques' -ar 'رياضيات'      # once a teacher confirmed the names
go run ./cmd/server set-chapter-name -subject maths -code complexes -fr 'Nombres complexes'
go run ./cmd/server set-order -subject maths -chapter complexes -order 3                 # without -chapter: the subject
go run ./cmd/server show-catalogue                                                       # or -subject maths
read -rs PW && printf '%s\n' "$PW" | go run ./cmd/server create-user -email teacher@example.test -name 'Teacher Name'; unset PW
go run ./cmd/server grant -email teacher@example.test -permission author                    # writes lessons
go run ./cmd/server grant -email reviewer@example.test -permission reviewer -subject maths   # reviews maths
```

Codes are 1 to 63 lower-case ASCII letters, digits and hyphens, not starting with a hyphen (the `subjects`/`chapters` CHECK constraints); anything else, an unknown subject for `add-chapter`, and extra arguments are refused before the database is touched. Each addition writes the entry and an append-only `catalogue_audit` row (operator label, action, subject, chapter, transaction time; `migrations/0010_catalogue_audit.sql`) in one transaction; the database refuses at commit any subject or chapter inserted without that row (tests use `dbtest.SubjectSQL` and `dbtest.ChapterSQL`). Repeating an addition prints `no change: … already exists`, exits 0 and writes nothing. Codes never change and entries are never deleted.

Display names and order (issue #86, `migrations/0012_catalogue_names.sql`) are mutable display metadata. `set-subject-name` and `set-chapter-name` set the French (`-fr`) and/or Arabic (`-ar`) name; a flag left out keeps that name, and names cannot be removed from the command line. A name is trimmed and must then be 1 to 200 characters without control, format (invisible or bidirectional) or line/paragraph separator characters; Arabic is accepted. `set-order -order N` takes 0 to 9999 (all entries start at 0); lists sort by order, then code. `show-catalogue` prints every subject and its chapters in that order, with IDs, orders and names (`-` when unset). Each change writes the new values and a `catalogue_audit` row (`rename_subject`, `rename_chapter`, `reorder_subject` or `reorder_chapter`, with the old and new values and the operator label) in one transaction; the database refuses a name or order change without its matching audit row of the same transaction, and an audit row whose change was not made. Setting the current values prints `no change: …` and writes nothing. Invalid input, unknown codes and extra arguments are refused before the database is touched. Names are not part of any lesson revision: renaming a chapter changes how published lessons placed in it are labelled in the reader and the Studio, without a review. It is an administrator catalogue action ([CAHIER_DES_CHARGES.md](CAHIER_DES_CHARGES.md)); only set names a teacher has confirmed. The pilot catalogue itself is LRN-014: there is deliberately no seed data. Teachers sign in at `/login` and open `/studio`.

### Curriculum hierarchy (LMS-B02)

Levels, sections, editions and their subject assignments are maintained by an administrator through `/api/admin/curriculum/…` ([API.md](API.md#curriculum-lms-b02)); no curriculum is seeded and there is no operator command for it yet. Subjects and chapters still come from `add-subject` and `add-chapter`. A typical sequence with TEST data: create a level, a section under it and a draft edition; assign subjects and set each assignment's ordered chapter list; make the edition current (`expectedCurrentEditionId: null` for the section's first edition). Assignments freeze once the edition leaves draft: a change of meaning is a new edition, made current in its turn, which supersedes the previous one. Every change is in `curriculum_audit`.

### Courses (LMS-B03)

Authors create courses and edit their drafts through the [course draft API](API.md#course-drafts-lms-b03); there is no Studio page or operator command yet. A typical sequence with TEST data: `POST /api/courses` with a subject and language (an empty first draft), search attachable lessons, then `PUT` the whole draft (overview, cover, assignments of a current edition, modules and steps) with its `expectedVersion`. Only drafts exist until course review lands (B04).

### Studio in the application

The application server serves the built Studio at `/studio` (issue #65, [API.md](API.md#studio-integration-issue-65)): build it once, then point `LEARNOO_STUDIO_DIR` at the output.

```sh
(cd web/studio && npm ci --ignore-scripts && npm run build)   # writes web/studio/dist, base /studio/
LEARNOO_MEDIA_DIR="$HOME/.local/share/learnoo/media" LEARNOO_STUDIO_DIR="$PWD/web/studio/dist" \
  go run ./cmd/server serve                                    # http://127.0.0.1:8090/studio
```

Client routes of the Studio must not have a dot in their last segment: the server treats such paths as files (404 when missing) and every other path under `/studio/` as a route that gets `index.html`. Rebuild after changing the Studio; the server reads files on each request and caches nothing. Anonymous visitors are sent to `/login?next=/studio`; accounts without `author`, `publisher`, `administrator` or a reviewer assignment (students) get a 403 page. The Studio calls the same-origin API with the session cookie and the CSRF token from `GET /api/auth/session`: catalogue (`/api/catalogue/…`), the author's lessons (`/api/lessons/mine`), drafts (`/api/lessons`, `/api/revisions/…`), media (`/api/media`) and the canonical preview (`POST /api/preview`, rendered by `internal/rendering`).

#### Using the Studio (authoring)

Sign in as an account with `author` (and add at least one subject with `add-subject`; chapters are optional). Routes: `/studio/` lists your lessons, `/studio/lessons/new` starts one, `/studio/lessons/{lessonId}/edit` opens a lesson's latest revision.

- **My lessons** shows each lesson's title, subject, chapter, language, state (Brouillon, En relecture, Modifications demandées, Approuvée en attente de publication, Publiée), revision number and version, and "Retour du relecteur à traiter" when a reviewer requested changes.
- **New lesson**: pick the subject and optional chapter from the catalogue, the language (French or Arabic, fixed afterwards) and optionally one of your lessons of the same subject as translation source. The lesson is created on the server by the first **Enregistrer** (`POST /api/lessons`), since a lesson must start with a valid draft.
- **Saving** is explicit (button or `Ctrl/Cmd+S`) and version-checked (`PUT` with `expectedVersion`). The save status is announced politely to screen readers. If another tab or device saved first, a conflict panel keeps your edits in the editor and offers to load the server version (your version then stays offered as a local copy to restore or copy) or to copy your content. Leaving the page or signing out with unsaved edits asks first.
- **Recovery copies**: while edits are unsaved, a copy is kept in this browser's `localStorage` (crash protection only, see DECISIONS.md). It is offered, labelled "Copies de secours locales (non enregistrées)", the next time the lesson is opened (also on a later version of the lesson, if the draft was submitted or deleted meanwhile), and deleted once its content is saved or when you delete it. Signing out deletes your copies from the browser (with a warning first); copies older than 14 days are deleted when the Studio starts. Copies are never sent to the server by themselves.
- **Session expired, or another account signed in**: a banner says so; nothing on the page is discarded and nothing is sent. Sign in again with your own account (in a new tab), then choose "Reprendre ici" and save. A tab never saves, uploads or creates as an account other than the one it was opened with.
- **Submitted elsewhere**: if another tab submitted the draft, saving explains it, keeps your edits and offers them as a copy on the submitted revision and the next version.
- **Images**: upload PNG, JPEG or WebP (5 MiB, 4096 px per side) with "Téléverser une image". Server refusals are explained (for example `trailing_data`: re-export the image or save it as PNG). Uploads are attached to the revision as immutable media references (`mediaIds`), saved with the draft and frozen at submission. "Placer dans le texte" inserts an attached image at the cursor after asking for its alternative text (required) and an optional caption; the inspector edits both. Placed images appear in the preview, on the review and publication pages and, once published, in the student reader (issue #77). An image removed from the text stays attached until "Retirer de la révision".
- **Preview** (`POST /api/preview`) shows the reader's exact markup in the page, styled by the reader's `site.css` and `reader.css` (scoped under `.lesson-preview` at build time) and typeset with the KaTeX the server names in `index.html` (fingerprinted under `/assets/`; the development server, whose `index.html` has no such names, falls back to `/static/vendor/katex/`; run `npm run assets` first). Videos are not loaded in the preview.
- **Submit** asks for confirmation, saves pending edits, then `POST …/submit`. A submitted revision is read-only; after a change request the reviewer's comment is shown and "Créer la version corrigée" starts the successor draft (`POST /api/lessons/{id}/drafts`). The server's `active_candidate_exists` refusal (a draft, a revision in review or an approved revision awaiting publication) is explained.
- **Delete a draft** asks for confirmation (`DELETE` with `expectedVersion`).
- Accounts without `author` see the spaces they can use instead.

#### Using the Studio (review, publication, administration)

Each space appears in the Studio navigation only when the server lets the account use it (each is probed once at start-up through its own read endpoint; a `403` hides it). Navigating to a space anyway shows "Accès refusé", and the server refuses its requests regardless.

- **Relecture** (`/studio/review`, a reviewer assignment): revisions in review in your subjects, grouped by subject, oldest first; your own revisions are not listed. A revision (`/studio/review/revisions/{id}`) shows its author, subject, chapter, language, prerequisites, attached images (`/api/review/media/{id}`) and the canonical preview. "Approuver…" (optional comment) and "Demander des modifications…" (comment required, checked before anything is sent) both ask for confirmation. Opening your own revision explains that another reviewer must review it and shows no decision buttons (the server answers `403 self_review` anyway).
- **Publication** (`/studio/publish`, `publisher`): approved revisions awaiting publication; a revision whose base is no longer the published revision is flagged "Base périmée" and shows no publish button. `/studio/publish/revisions/{id}` shows the preview and "Publier cette révision…" (confirmed), then links to the reader page and the lesson's publication history.
- **Signalements** (`/studio/reports`, reviewers and administrators): reports filtered by status; a report (`/studio/reports/{id}`) shows the reader's message as plain text, links to the published lesson, and closes as "corrigé" or "écarté" with a required note (confirmed; a report cannot be reopened).
- **Administration** (`/studio/admin`, `administrator`): find a lesson by public ID, reader address or number, or pick it from the list of approved or published lessons. The publication page (`/studio/publication/{lessonId or publicId}`, also open to publishers) shows the published revision, every submitted revision with its state, and the pointer history. Administrators withdraw a revision (reason required, final) or unpublish in an emergency (reason required); publishers and administrators restore a revision published before. Each confirmation names the published revision the page loaded; if it changed meanwhile, the server refuses with `stale_pointer`, nothing changes, and "Recharger l’état actuel" shows the new state.

Browser tests: `tests/browser-reader/editorial.spec.mjs` (run by `npm run test:reader`) signs in as the fixture's TEST accounts: `test-author`, `test-reviewer` and `test-reviewer-b` (reviewers of `test-math`), `test-reviewer-physique` (reviewer of `test-physique` only), `test-author-reviewer`, `test-publisher`, `test-admin` and the invited student `test-student`.

Development server: `cd web/studio && npm run dev` serves the Studio on http://127.0.0.1:5173/studio/ and proxies `/api`, `/static`, `/login` and `/logout` to a running application server (`LEARNOO_APP_URL`, default `http://127.0.0.1:8080`; `LEARNOO_STUDIO_PORT` changes 5173), keeping the browser's `Host` so the server's same-origin checks pass. Sign in through the proxied `/login`. The renderer experiment is not used.

Try it (curl stores `Secure` cookies for `127.0.0.1`; browsers do the same for loopback):

```sh
curl -s -c jar -H 'Content-Type: application/json' \
  -d '{"email":"you@example.test","password":"…"}' http://127.0.0.1:8090/api/auth/login
curl -s -b jar http://127.0.0.1:8090/api/auth/session
```

Studio endpoints need the `author` permission. Grant it with the operator command above:

```sh
go run ./cmd/server grant -email you@example.test -permission author
```

Then sign in and call the Studio API. The password and CSRF token are passed on stdin, never as command-line arguments (`-H @-` reads headers from stdin; curl 7.55 or newer):

```sh
read -rs PW && printf '{"email":"you@example.test","password":"%s"}' "$PW" \
  | curl -s -c jar -H 'Content-Type: application/json' --data-binary @- \
      http://127.0.0.1:8090/api/auth/login > session.json; unset PW
CSRF=$(sed -n 's/.*"csrfToken":"\([^"]*\)".*/\1/p' session.json)
# lesson.json: {"subjectId": 1, "language": "fr", "content": {…schema v1 document…}}
printf 'X-CSRF-Token: %s\n' "$CSRF" | curl -s -b jar -H @- -H 'Content-Type: application/json' \
  --data-binary @lesson.json http://127.0.0.1:8090/api/lessons
printf 'X-CSRF-Token: %s\n' "$CSRF" | curl -s -b jar -H @- -H 'Content-Type: image/png' \
  --data-binary @diagram.png http://127.0.0.1:8090/api/media
curl -s -b jar -o served.png http://127.0.0.1:8090/api/media/1
rm -f jar session.json
```

### Invite a student and use the reader (LRN-008)

```sh
go run ./cmd/server invite-student -email student@example.test            # valid 72 hours
go run ./cmd/server invite-student -email student@example.test -ttl 24h   # 1h to 720h
```

The command prints the invitation ID, the normalized email, the expiry and the operator label (`<os user>@<hostname>`, self-asserted), then a one-time link such as `http://127.0.0.1:8090/invite/<token>`. Nothing secret is read from the command line: the email is not a secret and the token is generated by the command. Only the token's SHA-256 is stored, so the link cannot be shown again; if it is lost, issue a new invitation. Treat the link like a password: send it privately, never paste it into issues, chats with others or shared logs. An email that already has an account is refused. Opening the link lets the invited person choose a display name and a password (12 to 1024 characters); the account has no permissions (a Student) and is signed in straight away. Each link works once and expires.

**Real students:** do not invite real students yet. The privacy, retention and deletion policy is undecided and the pilot preparation is LRN-011 ([DECISIONS.md](DECISIONS.md#student-reader-lrn-008)). Use simulated addresses such as `@example.test` locally.

The reader is at `http://127.0.0.1:8090/learn` (sign-in page `/login`). It lists only lessons with a published revision; publish a TEST lesson through the Studio and review API first. Routes and headers: [API.md](API.md#student-reader-lrn-008).

Subjects and chapters have no seed (LRN-014); add simulated ones with `go run ./cmd/server add-subject -code simulated-math` and `add-chapter -subject simulated-math -code …` ([Provisioning teachers and the catalogue](#provisioning-teachers-and-the-catalogue)). A plain `INSERT INTO subjects` fails at commit because every subject and chapter needs its `catalogue_audit` row of the same transaction, and a plain `UPDATE` of a name or order fails for the same reason; use `set-subject-name`, `set-chapter-name` and `set-order` (TEST names only in fixtures). Subjects and chapters are read by `GET /api/catalogue/…` ([API.md](API.md#catalogue)).

Endpoints, errors, CSRF, authorization and throttling are specified in [API.md](API.md).

### Deployment and recovery commands (LRN-010)

`server verify-restore [-strict]` checks a restored database and media directory (`LEARNOO_DATABASE_URL`, `LEARNOO_MEDIA_DIR`) and prints a report; `server probe [-path /readyz]` is the container health check. The Dockerfile, the production Compose file, the database role scripts and the backup/restore scripts are described in [DEPLOYMENT.md](DEPLOYMENT.md). `GET /healthz` is liveness and `GET /readyz` readiness ([API.md](API.md#get-healthz)). The root `compose.yaml` stays a local development database only.

### Migrations

Files live in `migrations/` as `NNNN_description.sql` and are embedded in the binary. Each runs in its own transaction under a PostgreSQL advisory lock; `schema_migrations` records a SHA-256 checksum of each file. The runner refuses a database whose history contains an unknown version, an edited file or an out-of-order gap. Never edit a merged migration: add the next number. Only one open PR adds migrations at a time ([§5.4](CAHIER_DES_CHARGES.md#54-shared-contracts-agree-first-then-build-in-parallel)).

### Tests

```sh
go test ./...
go vet ./...
```

On a shared test database with PostgreSQL's default `max_connections` of 100, bound package parallelism: `go test -p 2 ./...` (up to `-p 4`). Each database-backed test gets a schema pool capped at 8 connections (`dbtest.EmptySchema`) plus an admin connection, and no test calls `t.Parallel`, so a package uses about 9 connections at a time; concurrency tests warm up to 6 of them at once. Unbounded `-p` (one package per CPU) can exhaust the server. `dbtest.Warm` gives up after 30 seconds and releases every connection it took, so an exhausted server fails the test instead of hanging its cleanup until the 10-minute test timeout.

With `LEARNOO_TEST_DATABASE_URL` set, each database-backed test creates an isolated schema, migrates it and drops it afterwards, so tests may run in parallel and leave nothing behind. They cover migration repeatability and tamper detection, cookie attributes, enumeration-safe errors, anonymous access, idle and absolute expiry, rotation on login, logout revocation, CSRF rejection, strict login JSON (exact, unique keys), per-account and per-address throttling and concurrent attempts, plus permission deny-by-default, per-subject reviewer scope, no implied permissions (reviewer never implies publisher), administrator-only grants, audit records and their append-only protection, the operator commands (bootstrap, grant, revoke, disable-user, enable-user, show-user, invalid input leaving the database unchanged, the operator label in both audits), account disable and enable (session revocation, enable purging sessions, the last-administrator refusal, the status audit's exactly-one-actor and label constraints and its append-only protection), concurrent bootstrap, concurrent revocations and disables of the last two administrators in every mix (by the operator, and by the two administrators acting on each other, which must not deadlock), logins racing a disable (no session survives, the refused login is indistinguishable from a bad password), and type-checked source scans. One scan fails if `internal/server` or any module package it imports refers to `permissions.OperatorAs`. The other, over every module package, allows `permissions.Store` change methods and `OperatorAs` only in `cmd/server/main.go` and `internal/permissions/permissions.go`, allows `accounts.Store.Disable` and `Enable` only in `cmd/server/main.go`, flags any of them inside any function taking an `http.ResponseWriter`, flags SQL literals that write `user_permissions`, `reviewer_assignments` or `permission_audit` outside `internal/permissions`, and flags SQL literals that write `account_status_audit` or set `users.disabled_at` outside `internal/accounts` (disabling an account can remove an active administrator, so it must go through the last-administrator guard). ## Local renderer experiment

This is the LRN-004 renderer experiment, not the production application. It deliberately has no accounts, database, teacher workflow or publishing. It binds only to 127.0.0.1 and accepts only fixtures marked `unreviewed`. Do not expose it through a public reverse proxy or tunnel.

### Prerequisites

- Go 1.25 or newer (tested with 1.25.4).
- Node.js 22 and npm (tested with Node 22.20.0).

### Run

From the repository root:

```sh
npm ci --ignore-scripts
npm run assets
go run ./cmd/renderer
```

Open http://127.0.0.1:8080/lesson. Change the local port with `go run ./cmd/renderer -port 8081`.

- `/`: landing-page UI example; local only, no registration or publication.
- `/lesson`: unreviewed French complex-numbers fixture.
- `/bidi`: isolated Arabic/French directionality fixture.
- `/failure`: intentionally invalid formula with readable fallback.
- `/lab`: edit raw JSON, preview with the same Go renderer, save/reopen on the current browser only.
- `POST /preview`: validates JSON and returns the canonical HTML used by the reader.

Browser-side KaTeX is copied from the pinned npm package and served locally with its license. No CDN requests are needed. YouTube loads only on a click when an actual video ID is present; the initial lesson has a pending-selection placeholder. The original logo banner is not loaded on every lesson page.

The JSON laboratory is not TipTap. No server-side draft storage or approval behavior is simulated. See [fixture details](fixtures/README.md).

### Design foundations

The reader consumes generated design tokens. Edit `web/design/tokens.json`, run `npm run design:build`, and rebuild the Go server. See [shared design exports](../web/design/README.md) for plain CSS and future Tailwind v4 Studio integration.

## Studio editor (LRN-003, issue #66)

`web/studio` is the React/TypeScript/TipTap authoring application with its own `package.json` and lockfile, built with Vite `base: '/studio/'` and served by the application server (see [Using the Studio](#using-the-studio-authoring)). It edits the restricted lesson JSON through a validated adapter and saves only to the server. Verified versions: React 19.3.1, TipTap 3.35.0, Vite 8.3.8, TypeScript 6.0.3, Vitest 5.1.1, jsdom 29.1.1, on Node 22.20.0.

Checks, from `web/studio`:


`npm test` covers fixture round trips, stored revisions opening and saving back unchanged, paste filtering, invalid input, the Go-parity cases in `test/contract/cases.json` (which `go test ./internal/rendering` also runs), the API client (CSRF handling, account changes, typed errors, raw image uploads), save outcomes (version conflict, submitted draft, retry, expired session), the recovery buffer (lesson-wide lookup, sign-out and age purge) and the reader-CSS scoping used by the preview. `test/golden/studio-features.json` is an editor-authored export that Go validates and renders; regenerate it deliberately with `UPDATE_GOLDEN=1 npm test`. ### Continuous integration

[`.github/workflows/ci.yml`](../.github/workflows/ci.yml) runs the commands above on every pull request to `develop` or `main` (including fork PRs) and on pushes to those branches. GitHub reports the check as **`verify`** under the **CI** workflow; select that check from the list when configuring branch protection rather than typing a name. It runs on Ubuntu 24.04 with Go 1.25.x and Node 22, in this order: `npm ci --ignore-scripts`, `npm run design:check`, `npm run assets`, `npm run design:contrast`, then in `web/studio` `npm ci --ignore-scripts`, `npm run typecheck`, `npm test`, `npm run build`, then `go test ./...`, `go vet ./...`, `npx playwright install --with-deps chromium`, `npm run test:browser`, `npm run test:reader`. Any failing step fails the job; no step is allowed to fail. Before `go test` it checks that `psql`, `pg_dump` and `pg_restore` (preinstalled on the runner) are available for the deployment rehearsal tests. A second job, **`image`**, builds the application `Dockerfile` (no push, no secrets) and checks that the image runs as uid 65532 and contains the server but no renderer experiment. A `postgres:16.13` service container (loopback port, trust authentication, no secret) backs the database tests; the job sets `LEARNOO_TEST_DATABASE_URL` and `LEARNOO_REQUIRE_DB_TESTS=1`, so those tests fail rather than skip if the database is unreachable.

Security: the workflow uses the `pull_request` trigger (never `pull_request_target`), a read-only `contents: read` token, no repository secrets, and checkout without persisted credentials. Third-party actions are pinned to commit SHAs. If a step fails, the `test-results/` folder (local fixture screenshots and metrics only) is uploaded as the `playwright-test-results` artifact for 7 days.

`design:check` runs before `assets` on purpose: `assets` regenerates the design files, so checking afterwards would hide generated CSS that was not committed. Making `verify` a required status check in branch protection is a maintainer setting and is not changed by the workflow.

### Security limits

Schema allowlists, escaped templates, local image allowlists, content/depth/formula limits, CSP, same-origin preview checks, and KaTeX `trust: false` reduce rendering risks. They do not establish production security. For the renderer experiment, the only HTTP mutation is a read-only rendering request. The authenticated application (`cmd/server`) enforces authentication, durable storage, role checks, review and publication invariants on the server; the Studio's controls are a convenience, never the enforcement.
