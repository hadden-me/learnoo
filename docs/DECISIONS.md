## Application server foundation (LRN-005)

Implementer choices for the foundation slice on 2026-11-24 (role model still open; nothing here grants or checks permissions):

- `cmd/server` is separate from `cmd/renderer`; the renderer stays an isolated loopback experiment. The server also binds only to loopback by default; the production Compose file opts out explicitly (LRN-010, see [Deployment and recovery](#deployment-and-recovery-lrn-010)), and the trusted proxy chain is still undefined.
- PostgreSQL 16 through `pgx/v5`. Migrations use a small embedded runner (per-file transaction, advisory lock, SHA-256 checksums that reject edited, unknown or out-of-order history) instead of an external migration tool, to avoid a dependency for about 150 lines of logic.
- Passwords: Argon2id from `golang.org/x/crypto/argon2`, PHC string format, OWASP minimum cost (19 MiB, t=2, p=1) chosen for the shared server's memory. Parameters are stored per hash, so they can be raised later. Unknown and disabled accounts are verified against a dummy hash to keep timing and responses identical.
- Sessions: 256-bit random tokens; only their SHA-256 is stored. Cookie `__Host-learnoo_session`, `HttpOnly`, `Secure`, `SameSite=Lax`. Idle timeout 24 hours, absolute 14 days. Login always issues a new token and revokes any presented session; logout deletes the row.
- CSRF: Go's `http.CrossOriginProtection` on every unsafe request (including login), plus a per-session token in `X-CSRF-Token` for authenticated mutations. Login accepts only `application/json`.
- Throttling in PostgreSQL (no Redis): attempts are recorded before the password check under per-key advisory locks; more than 5 per email or 30 per client address in a sliding 15-minute window returns 429. Keys are stored as SHA-256 hashes, not raw emails or addresses. Accepted risk: an attacker can temporarily lock a known email out; revisit with LRN-022 public-launch hardening.
- `create-user` reads the password from stdin and creates an account without roles; it is an operator tool, not registration. Role grants are the LRN-013 operator commands (see "Role administration CLI").

## Exact-key JSON decoding (issue 41)

Go's `encoding/json` matches keys to struct fields case-insensitively, including Unicode folding (`ſrc` fills `src`, the Kelvin sign U+212A matches `k`), and keeps the last of duplicate keys. A lesson could then carry an allowed `src` that Go validated beside an unsafe one that an exact-key reader would use. From 2026-11-24, lesson JSON (`rendering.Decode`) and the login request go through `internal/strictjson`: keys must equal a field's JSON name byte for byte, each key appears once per object at every level, and only whitespace may follow the single value. The Studio's `parseLesson` applies the same rules; shared contract cases cover them. This is stricter validation only: `schemaVersion` stays 1 and every existing fixture and export is unchanged. Later JSON endpoints should decode through the same package.

## Null values and number spellings in lesson JSON (issue 43)

`encoding/json` treats `null` in a non-pointer field as absent and refuses `1.0` or `1e0` for an `int`, while `JSON.parse` refuses `null` where text or a list is expected but reads `1.0`, `1e0` and `1.00000000000000001` as `1`. From 2026-11-24 both sides reject them: `internal/strictjson` refuses `null` unless the target is a pointer or interface, and refuses any integer-target number that is not a plain in-range integer literal; the Studio's `parseLesson` refuses every number literal that is not a plain integer within int64 range (the only numeric field is `schemaVersion`). Shared contract cases cover each spelling. Stricter validation only: no fixture or export uses these spellings, and `schemaVersion` stays 1. The login request decodes through the same package, so `null` there is now a decode error (still 400).

## Permission storage (LRN-005)

Implementer choices on 2026-11-24, following the confirmed role model: global permissions (`author`, `publisher`, `administrator`) in `user_permissions`; per-subject reviewer grants in `reviewer_assignments`; an append-only `permission_audit` (database triggers reject update, delete and truncate). Account types are not stored; they are derived from permissions. A bare `subjects` table (`id`, unique `code`, no seed) exists only as the reviewer scope; LRN-014 extends and seeds it. Only an active `administrator` (or a trusted local operator tool) can grant or revoke. Administrators may assign themselves as subject reviewers; self-approval of their own revisions remains forbidden and is enforced in LRN-007. Removing the last administrator is prevented since LRN-013 (see "Role administration CLI"). Changes by an administrator share-lock the actor's own administrator grant, so two administrators revoking each other at the same time cannot both succeed; since LRN-013 administrator changes take the administrators lock first, so the second one waits and is then denied instead of deadlocking. Grant and audit times are the database transaction time.

Append-only enforcement relies on triggers, which constrain only roles that neither own `permission_audit` nor are superusers: the owner can disable or drop the triggers, and a superuser can also skip them (`session_replication_role`). Tests run as the owning role and prove the triggers, not the privilege boundary. The deployed application must connect as a least-privilege role that does not own the tables; creating that role and running migrations under a separate owner is deployment work (LRN-010).

## Operator trust boundary

Recorded 2026-11-24 for LRN-005 and the LRN-013 CLI. Anyone with local database access can already change every table, so the code treats such a person as an operator: operator actors skip authorization and are meant only for local tools (the LRN-013 role CLI). To meet the audit requirement (actor, target and time for every role change, [CAHIER_DES_CHARGES.md §2.2](CAHIER_DES_CHARGES.md)), operator changes are recorded with `actor_id` NULL and an `operator_label`; a database constraint requires exactly one of the two on every audit row. CLIs must build their actor with `permissions.OperatorAs(permissions.LocalOperatorLabel())`, which records `<os user>@<hostname>` (falling back to `unknown` for either part). The label is self-asserted, not authentication: it identifies who ran the tool for honest operators, but anyone with database access could write any label, so the trust boundary stays "local database access = operator". Labels are 1 to 200 characters, trimmed, with no control (Cc), format (Cf, including invisible and bidirectional controls such as U+200B or U+202E) or line/paragraph separator (U+2028, U+2029) characters, so an append-only audit label cannot display as a different identity; the database enforces the same rule with an explicit code-point list that does not depend on the locale, and the Go check is at least as strict. `OperatorAs` is the only way to build an operator actor: there is no unattributed operator, so every operator change carries a label. Operator actors must never be reachable from HTTP code: a test type-checks `internal/server` and every module package it imports (other than `internal/permissions`) and fails on any reference to `OperatorAs`. Signed-in users change permissions only as `permissions.UserActor`, must hold `administrator` at the time of the change, and are audited by `actor_id` with no label.

## Role administration CLI (LRN-013)

Implementer choices on 2026-11-25:

- **Trust boundary.** Permissions and account status are administered by `cmd/server` operator commands (`bootstrap-admin`, `grant`, `revoke`, `disable-user`, `enable-user`, `show-user`). They act as `permissions.OperatorAs(permissions.LocalOperatorLabel())`: permission and account status changes are both audited with no `actor_id` and the self-asserted `<os user>@<hostname>` label (see "Operator trust boundary"), which `show-user` prints. Being able to run them with a database URL that can write the schema is the trust boundary: local database access = operator, so database credentials must be held like administrator credentials. No HTTP route changes permissions or account status; besides the HTTP-layer scan for `OperatorAs`, a type-checked source test fails if the `permissions.Store` change methods or `OperatorAs` are used outside `cmd/server/main.go` and `internal/permissions/permissions.go`, if `accounts.Store.Disable` or `Enable` are used outside `cmd/server/main.go`, if any of them is used inside an HTTP handler, or if SQL literals outside the owning package write the permission tables (`internal/permissions`) or `account_status_audit` or `users.disabled_at` (`internal/accounts`) (details in DEVELOPMENT.md). A web console (LRN-019) will act as `UserActor` and needs its own review.
- **First administrator.** `bootstrap-admin` creates the account and grants the Administrator defaults in one transaction, refused (`permissions.ErrAdministratorExists`) while any active administrator exists. `Store.Bootstrap` refuses any actor that is not an operator. Later administrators are granted with `grant`. `bootstrap-admin` never adopts an existing account: an already-registered email is refused with nothing changed, and an existing account is made administrator with `grant`.
- **Last-administrator rule.** An active administrator holds `administrator` and has `users.disabled_at IS NULL`. Revoking `administrator` from, or disabling, the only active administrator fails with `permissions.ErrLastAdministrator` for every actor, operator included; it is enforced in `internal/permissions` (and by `internal/accounts` through it), not in argument parsing. Revoking it from a disabled account is allowed, since it does not change the active count. Recovery when no active administrator remains (for example, all were disabled directly in SQL) is a new `bootstrap-admin`.
- **Concurrency.** Every operation that can add or remove an active administrator (`Bootstrap`, `GrantDefaults` for an Administrator, granting or revoking `administrator`, disabling or enabling an account) first takes one transaction-scoped advisory lock (`pg_advisory_xact_lock`), then counts. At READ COMMITTED each statement sees the previous holder's commit, so two concurrent revocations or disables (in any mix) against the last two administrators leave exactly one, and two concurrent bootstraps produce one administrator. The order is load-bearing: `LockAdministrators` first, then `Authorize` (which takes `FOR SHARE` on the actor's grant), then `GuardAdministratorRemoval` and the change. Taking the advisory lock after `authorize` lets two administrators revoking each other deadlock (SQLSTATE 40P01); a test covers it. Code outside the package that removes an active administrator (as `internal/accounts` does) must follow the same order.
- **Account status.** `internal/accounts` disables and enables accounts. Disabling sets `users.disabled_at` and deletes the account's sessions in the same transaction; enabling clears it and also deletes any sessions, so the account always starts clean. Grants are kept (a disabled account already holds no effective permissions). Only an operator or an active administrator may change account status. Each effective change is recorded in the append-only `account_status_audit` table (`migrations/0003_account_status.sql`: actor, target, `disable`/`enable`, and the database transaction time, equal to `disabled_at`); repeats are no-ops without an audit row. As in `permission_audit`, the actor is exactly one of `actor_id` (a signed-in administrator) and `operator_label` (an operator tool), enforced by a database constraint whose label rule is identical to `permission_audit_operator_label`.
- **Disable racing other work.** Login's session transaction first locks the account's `users` row `FOR SHARE` and re-checks `disabled_at`; a disable updates that row before deleting sessions. So a login that passed the password check just before a disable either fails with the usual `invalid_credentials` (enumeration-safe) or commits a session that the waiting disable then deletes. `Authorize` likewise locks the actor's `users` row (`FOR SHARE OF p, u`), so an administrator's change cannot commit after that administrator is disabled. Every transaction that touches both takes the `users` row before any session row, so disable and login cannot deadlock on each other; any other `40P01` from PostgreSQL is a transient, retryable failure and changes nothing.
- **Deleting audited accounts.** `permission_audit` and `account_status_audit` reference `users` with the default `NO ACTION`, so an account with audit rows cannot be deleted. Account deletion (LRN-022) must decide what to keep or anonymise, and must apply the last-administrator guard (`LockAdministrators`, then `GuardAdministratorRemoval`) before removing an administrator.

## Lesson persistence (LRN-006)

Implementer choices for the persistence core (slice 1, no HTTP endpoints) on 2026-11-24, within the maintainer-approved execution contract on issue 6.

- **Catalogue contract.** `subjects` (LRN-005) is the subject reference. A minimal `chapters` table holds `id`, `subject_id`, `code` (unique per subject, same format as subject codes) and `created_at`; no names, ordering or seed rows. A chapter's subject and code never change and chapters are never deleted or truncated (database triggers); identity values are never reused, so a chapter ID is never repurposed. Versioned curriculum assignments (IMPLEMENTATION_PLAN §6) are pending LRN-014.
- **Lesson identity.** `lessons` holds a random `public_id` (UUID, never derived from the title), `translation_group_id`, `language`, `subject_id`, `published_revision_id`, `archived_at`, creator and creation time. These identity columns are immutable; only the pointer and archive state change. A lesson's subject is fixed: each revision's `subject_id` and `language` must equal its lesson's (composite foreign key), so per-subject reviewer scope cannot be changed by a draft. A revision's `chapter_id` is optional until LRN-014 and must belong to that subject (composite foreign key); changing it requires a new revision.
- **Translations.** A `translation_groups` row fixes one subject; each lesson references (group, subject) through a composite foreign key, so every lesson of a group shares the subject, and a group holds at most one lesson per language. The store also requires the source lesson to exist, share the subject and not be archived (checked under a share lock).
- **Reviewed snapshot.** `lesson_revisions` stores title, objectives, prerequisites, the schema v1 content JSON (with embedded exercises and solutions), schema version, language, subject, chapter, author, base revision, creation/update/submission times and referenced media (`revision_media`). Title, objectives, language and schema version are copies of the document's fields, kept equal by a check constraint. Statuses are `draft`, `in_review`, `changes_requested` and `approved`; publication is the lesson's pointer, not a status, and withdrawal is left to LRN-009.
- **Canonical validation.** Content must be valid UTF-8 (invalid bytes are rejected, not replaced) and is compacted (`json.Compact`) before `rendering.Decode`/`Validate`, so the 128 KiB limit applies to the compact form whatever the input formatting. The store keeps only the canonical form: the decoded document re-encoded compactly, which must validate too. The decoder refuses case-folded and duplicate keys, but stored content can still be altered outside the store (direct SQL), so submission re-validates the stored snapshot and requires it to equal its canonical re-encoding (jsonb equality, under the revision lock). Content altered outside the store, including case-folded duplicate keys such as `SRC` or `ſrc` next to `src`, is rejected with `ErrInvalidContent`; PostgreSQL's spaced, reordered jsonb output of a canonical document still passes. NUL or invalid bytes rejected by PostgreSQL also return `ErrInvalidContent`. The store does not bound how much it reads; callers cap input size (the HTTP slice limits request bodies).
- **Published pointer.** The pointer may name only an `approved` revision of the same lesson, or be NULL (trigger, with a deferred composite foreign key as well). The transactional comparison with the expected published base and the publish/unpublish/restore actions remain LRN-007/LRN-009.
- **One active candidate.** A partial unique index allows one active candidate per lesson: a `draft`, an `in_review` revision, or an `approved` revision whose `candidate_closed_at` is NULL. `changes_requested` is not active: the revision is retained while its successor draft is created. The store also locks the lesson row while creating a draft and checks the same predicate, so concurrent creators get `ErrActiveCandidateExists`; the index holds independently of that lock and maps to the same error.
- **Approved but unpublished revisions (maintainer decision, 2026-11-24).** An approved revision that has not been published is an active candidate and blocks another draft until it is published or explicitly withdrawn. Consequences:
  - `lesson_revisions.candidate_closed_at` records when an approved revision stopped being the candidate. An AFTER trigger on `lessons` sets it when the published pointer first names the revision (after the approved-only guard has accepted the pointer, under the lesson row lock already held, so the lock order stays lesson, then revision). It is set once and never cleared or changed: the immutability guard permits exactly one change to an approved revision, `candidate_closed_at` from NULL to the transaction time (`now()`) with no other column changing, only from inside a trigger (`pg_trigger_depth() > 1`), and only while `current_user` owns `lesson_revisions`. The trigger depth alone proves nothing: any role can create temporary tables, functions and triggers (PUBLIC has `TEMP` on a database by default), and such a trigger's body runs at depth 2 as that role. The owner check closes that route, because the only trigger code that runs as the owner is a `SECURITY DEFINER` function the owner created. The publication trigger function is therefore `SECURITY DEFINER` with a pinned `search_path` (`pg_catalog, pg_temp`), names `lesson_revisions` through the schema of the table that fired it, refuses to run for a relation its owner does not own (such as another role's temporary `lessons` table), and is not executable by PUBLIC (firing a trigger needs no `EXECUTE`; creating one does). A direct `UPDATE` or a trigger of the application role, with any timestamp, is rejected, so no writer can release a lesson (and later approve a second never-published revision beside the first) without publication or an audited withdrawal, or backdate the closing time. A database test reproduces the temporary-trigger route with a non-owner role holding only `USAGE`, DML grants and `TEMP`, and checks that publication by that role still closes the candidate. A check constraint keeps it NULL for every other status.
  - A revision that was ever published stays closed. Unpublishing, publishing a successor and restoring an earlier revision (LRN-009 re-points to it) therefore never reopen a candidate or block drafts.
  - Publication and `CreateDraft` both lock the lesson row first, so a draft started while a publication is in flight waits and is then based on the newly published revision; it is never created against the stale pointer.
  - **Until LRN-007/LRN-009 exist, there is no code path to publish or withdraw.** Once a revision is approved (also only by direct SQL until LRN-007), no further draft of that lesson can be created through the application. (LRN-007 adds approval and publication and LRN-009 withdrawal. See [Review and publication](#review-and-publication-lrn-007) and [Withdrawal, unpublication and restoration](#withdrawal-unpublication-and-restoration-lrn-009).)
  - The only release other than publication is withdrawal, which the editorial rules define as an administrative action against incorrect or unlawful content (CONTENT_AND_EDITORIAL.md, IMPLEMENTATION_PLAN §3 and §7), not an author's way to abandon an approved revision. A lesson whose approved revision should not be published therefore stays blocked unless an administrator withdraws that revision as incorrect. If this proves too strict, a separate audited "discard approved candidate" action would need its own decision.
  - LRN-009 withdrawal of an approved, never-published revision must close it through an audited trigger path, for example an AFTER INSERT trigger on the withdrawal audit table that sets `candidate_closed_at`, since the guard rejects direct updates. That trigger function must, like the publication one, be `SECURITY DEFINER`, owned by the owner of `lesson_revisions`, with a pinned `search_path`, a check of the firing relation, and `EXECUTE` revoked from PUBLIC; alternatively the index predicate must also exclude withdrawn revisions. Otherwise the withdrawn revision keeps blocking new drafts. LRN-007's publication-base check still blocks publishing a candidate whose base is stale. *Implemented by LRN-009 with the AFTER INSERT trigger on `revision_withdrawals`; see [Withdrawal, unpublication and restoration](#withdrawal-unpublication-and-restoration-lrn-009).*
  - **Open question (maintainer, before LRN-007/LRN-009): stale approved candidates.** If the lesson is unpublished, or restored to an older revision, while an approved candidate is pending, that candidate's `base_revision_id` no longer matches the published pointer. LRN-007's base check will then refuse to publish it, yet it keeps blocking new drafts, so the lesson is stuck until an administrator withdraws it. Separately, the restoration rule in CONTENT_AND_EDITORIAL.md ("previously approved, non-withdrawn revision", without the historical base check) would allow such a pending, never-published candidate to be published by restoration, bypassing the base check. Which behaviour is intended (for example: restoration limited to revisions that were published before; unpublication/restoration rejected or required to withdraw a pending candidate; or a stale approved candidate released automatically) is not decided. Nothing in this slice implements any of these. *LRN-009 keeps both parts open and takes the conservative reading: restoration is limited to revisions published before, and no automatic release is added (open questions in [Withdrawal, unpublication and restoration](#withdrawal-unpublication-and-restoration-lrn-009)).*
- **Revision numbers.** `lessons.last_revision_number` records the highest number used; an AFTER INSERT trigger requires each new revision number to exceed it and advances it, and the lesson guard rejects lowering it. Numbers are therefore never reused, even after a discarded draft (discarding #2 makes the next draft #3).
- **Lock order.** Every path locks the lesson row before a revision row: draft creation (lesson `FOR UPDATE`), save/submit/discard (lesson `FOR SHARE`, then revision `FOR UPDATE`) and the published-pointer triggers (lesson updated, then revision `FOR SHARE`, upgraded to an update of `candidate_closed_at` while the lesson row is still held). LRN-007's publish path must keep this order (lock the lesson first). If a future path breaks it, PostgreSQL resolves the resulting deadlock (40P01) by aborting one transaction; the HTTP layer should map 40P01 to a retryable conflict.
- **Base revision.** A new revision starts as `draft` and its `base_revision_id` must equal the lesson's current published revision (insert trigger); the store reads it under the lesson row lock.
- **Immutability.** A trigger rejects any change to a revision's identity columns, and, once it has left `draft`, to every column except `status`; `updated_at` may change only together with `status` (new columns are frozen by default). The one exception is closing an approved candidate (`candidate_closed_at`, see above). Status only moves forward: `draft` to `in_review`, then `changes_requested` or `approved`. Submitted revisions cannot be deleted; `revision_media` rows of a submitted revision cannot be inserted, updated or deleted (the guard share-locks the revision, so it cannot race a submission); truncation is rejected. `media_assets` rows cannot be updated, deleted or truncated: a replacement is a new asset. Lessons, users and subjects referenced by revisions cannot be deleted. Guard errors use SQLSTATE `LRN01`; guard triggers are named `zz_guard_*` because PostgreSQL fires BEFORE triggers in name order and a trigger modifying the row must run before them. Triggers that write other rows (closing a published candidate) are AFTER triggers, so they act only on rows the guards accepted.
- **Threat model.** The guards bind the application's database role, which must not be a superuser or own the tables. A superuser or table owner can bypass them (`session_replication_role = replica`, `ALTER TABLE … DISABLE TRIGGER`, dropping constraints or triggers). Deployment (LRN-010) must run the server under a separate least-privilege role with only the needed DML grants, distinct from the role that owns the schema and runs migrations. Every trigger function in the lesson migration pins `search_path = pg_catalog, pg_temp` (`pg_temp` last) and reaches any other table through the schema of the table that fired it (`TG_TABLE_SCHEMA`, `EXECUTE format('%I…')` with bound parameters). Otherwise a role with the default `TEMP` privilege could shadow a table a guard reads with a temporary table of the same name (`pg_temp` is searched first for relations): attaching media to a submitted revision, passing the approved-only pointer check, or forging a draft's base revision or reusing a discarded revision number. A database test tries each shadow as a non-owner role on a fresh connection (PL/pgSQL caches plans per session) and fails if the qualification is reverted. As defence in depth, the runtime role should also have no `TEMP` privilege on the database (revoke it from PUBLIC and grant it to no runtime role) and no `CREATE` on any schema, so it cannot create tables, functions or triggers at all; the guards' schema qualification and owner checks do not depend on this. `SECURITY DEFINER` trigger functions (currently `lessons_close_published_candidate`) run as the owner and must keep a pinned `search_path` and no PUBLIC `EXECUTE`. Until then the local and test setups use one role and the guarantees are only as strong as that role.
- **Optimistic saves.** Each draft has an integer `version`. Saves, submission and discard name the version they were based on; a mismatch returns `ErrVersionConflict` and writes nothing. Content, metadata and media references are replaced in one transaction.
- **Authorization.** Create, save, submit and discard require the `author` permission, checked inside the transaction with the grant and account rows share-locked (`permissions.RequireTx`), so a concurrent revocation or disablement waits until the write commits. Only a draft's author may save, submit or discard it; saves and submission are rejected while the lesson is archived. Starting a draft of an existing lesson, or a translation of it, is reserved to the lesson's owner (see "Lesson ownership" below). Read helpers perform no authorization, and the store distinguishes "not found" from "denied"; the HTTP slice must authorize reads and decide whether to merge the two so revision IDs cannot be probed.
- **Lesson ownership.** Maintainer decision of 2026-11-25 (issue 6): the lesson's creator (`lessons.created_by`) is its owner. Only the owner, while holding `author` (checked in the transaction with `permissions.RequireTx`, which share-locks the grant and account rows), may start a successor draft (`CreateDraft`); adding a translation (a new lesson in the source's translation group) requires ownership of the source lesson. Reviewers and publishers keep their separately granted capabilities; administrators get no implicit authorship and no review bypass. Anyone else gets `lessons.ErrNotOwner` (an `ErrDenied`), checked right after the lesson is found and before its state, so a non-owner learns nothing about archival or candidates; the Studio API answers it exactly like a missing lesson (`404 not_found` for a draft, `422 unknown_lesson` for a translation source). The database does not know who is acting, so it cannot check the actor's identity; that check is the store's (and the permission check is `RequireTx`). Its guards enforce the consistency the rule implies, for every writer: a revision's `author_id` must equal its lesson's `created_by`, and a lesson joining an existing translation group must have the `created_by` of the group's lessons, so each group has a single owner (`zz_guard_lesson_revisions_author_owns_lesson`, `zz_guard_lessons_translation_owner`, `migrations/0004_lessons.sql`). A direct writer with table access can still name any user as `created_by` of a new group or as `author_id` of a revision of that user's lesson; the guards only stop rows that contradict an existing owner. `created_by` never changes, so an owner read by a guard is never stale; a guard that sees no owner refuses (a lesson invisible to the transaction's snapshot, or a group with no visible lesson unless the current transaction created it), so a `REPEATABLE READ` writer whose snapshot predates another owner's group cannot join it. Consequently another author can no longer block a lesson with a draft of their own. A draft left by an owner who lost `author` or was disabled still blocks the lesson, and nobody else may continue it: ownership transfer and administrative draft recovery are separate scope (LRN-019/issue 9).
- **Discarding drafts.** An author may discard their own draft (it is deleted with its media references; the assets remain). There is no administrator discard: a draft left by an author whose permission was revoked or whose account was disabled blocks new drafts of that lesson until an audited administrative operation exists (pending, LRN-019/issue 9).
- **Submission audit.** Submission is recorded only by `submitted_at` and `author_id` on the revision. A review-event/audit record for submissions is deferred to LRN-007's review-event table. (LRN-007 did not add one; see the open question in [Review and publication](#review-and-publication-lrn-007).) *Since migration 0011 every submission is also recorded in the append-only `submission_audit`; see [Submission audit](#submission-audit).*
- **Media table only.** `media_assets` (SHA-256 unique, PNG/JPEG/WebP only, positive size and dimensions, a relative storage key without traversal) had no upload path in this slice; type sniffing, decoding and size limits live in `internal/media` (see Media upload limits below), and uploads arrive through the Studio API (see Studio API below). Schema v1 does not yet reference uploaded assets inside the document, so `revision_media` is supplied alongside it.

## Media upload limits (LRN-006)

Implementer choices for the media slice on 2026-11-24, in `internal/media` (not yet wired to the database or HTTP):

- Accepted: PNG, JPEG and WebP still images only, detected from magic bytes; filename and client `Content-Type` are never trusted. An empty declared type or `application/octet-stream` counts as undeclared; any other declared type that disagrees with the content is rejected. SVG, GIF, BMP, animated WebP, JPEG variants Go cannot decode (for example arithmetic coding) and everything else are rejected as unsupported.
- Polyglots: data after the image's end is rejected, not stripped: bytes after the PNG `IEND` chunk, after the JPEG `EOI` marker (found by walking segments and entropy-coded data, not by looking at the last bytes), or outside the WebP RIFF length. A RIFF length larger than the file is rejected as corrupt. The only exception is the phone-photo structures after a JPEG `EOI` listed below (issue 42).
- Phone photos (issue 42, 2026-11-25, `internal/media/jpeg.go`): after the primary JPEG's `EOI`, a trailer is accepted, and dropped, only if structurally validated parts and zero bytes cover it exactly. Accepted parts: (a) CIPA multi-picture (MPF) secondary images listed in the primary's single APP2 MPF index (version `0100`, at most 8 images, the primary entry at offset 0): each entry's offset and size must frame exactly one JPEG segment stream with a frame, a scan and its `EOI` as its last bytes, entirely after the primary; this covers iPhone and Android previews and Ultra HDR gain maps; (b) items of a Google `Container:Directory` in the primary's single standard XMP packet (Ultra HDR gain maps, motion photos): the first item must be `Primary`, the others are laid out one after another from the primary's `EOI` by `Item:Length` and `Item:Padding` (padding must be zero bytes); `image/jpeg` items are checked as in (a), a `MotionPhoto` item (`video/mp4` or `video/quicktime`) as an ISO BMFF box list that starts with `ftyp` and fills its length exactly; (c) a motion-photo video located by `GCamera:MicroVideo="1"` and `GCamera:MicroVideoOffset` (bytes from the end of the file), checked the same way; (d) zero bytes (`0x00` only) between or after those parts, at most 1 MiB in total (`MaxTrailingZeros`). A video must be the last part and end exactly at the end of the file: no image, declared padding or zero byte may follow it. In a video, a box size of 0 ("to the end of the file") is accepted only for a final `mdat` box (streaming writers produce it, and the declared length already bounds it); `ftyp` and every other box need an explicit size. The same range may be declared by two sources (a gain map is both an MPF entry and a Container item) only if both describe it identically. Everything else stays `ErrTrailingData`: unknown or partially covered bytes, overlapping or duplicated entries, lengths or offsets off by even one byte, several MPF segments, several Container directories or conflicting `MicroVideoOffset` values, unsupported items, a video without `ftyp`, and anything appended after a valid structure (PNG, ZIP, scripts). Why it is still safe: secondary images and videos are never decoded or parsed beyond their segment or box headers (the walk allocates nothing; only the primary's bytes reach the decoder), nothing from the trailer is stored (the primary is re-encoded as before), every byte of the trailer must belong to a structure whose bounds the primary's own metadata declares, and the 5 MiB upload limit, dimension limits and decode concurrency are unchanged. XMP is read with `encoding/xml` (no external entities) from one JPEG segment, so at most 64 KiB; a packet that is not well-formed, or several packets, claim nothing, so the trailer must then be covered by MPF alone. Properties written as XMP elements rather than attributes, and extended XMP, are not recognized. Samsung motion photos that end with Samsung's own index after the video (`SEFT`) remain rejected: that trailer is not described by XMP or MPF. A lone zero byte after `EOI` is now accepted padding, so the older test of a one-byte trailer uses a non-zero byte.
- EXIF orientation (issue 42): the Orientation tag (`0x0112`, one `SHORT`, values 1 to 8) is read with strict bounds from IFD0 of the primary's APP1 Exif segment and applied to the decoded pixels before re-encoding, so stored images are upright and still carry no metadata. Several Exif segments, a duplicate or ill-typed tag, an out-of-range value or a malformed TIFF structure are ignored (orientation 1, as stored) rather than rejected: the image still decodes the same way, nothing from EXIF is stored, and rejecting would refuse photos for unreadable metadata. Dimension limits are checked against the header and the upright size. Rotating allocates one `width × height × 4` RGBA buffer (at most 64 MB; grayscale: one byte per pixel) and reads the decoder's YCbCr, grayscale and CMYK outputs directly from their pixel buffers, without per-pixel allocations (a 16-megapixel CMYK image: 2 allocations, about 0.1 s; since the 2026-11-26 memory resolution CMYK JPEGs are refused and the direct path serves RGB-stored JPEGs instead); the source image is released as soon as the rotated copy exists. Peak figures are in "Limits" below. Orientation tags in PNG `eXIf` or WebP `EXIF` chunks are still ignored.
- HEIC/HEIF (issue 42, pending a maintainer decision on a vetted decoder): no decoder is added. HEIC/HEIF files (ISO BMFF `ftyp` with a `heic`, `heix`, `heim`, `heis`, `hevc`, `hevx`, `hevm`, `hevs`, `mif1`, `msf1` or `mif2` brand, not AVIF) are recognized from their bytes and rejected with `ErrUnsupportedHEIC` (which also matches `ErrUnsupportedType`); the upload API answers `415 unsupported_heic` (also for a declared `image/heic`/`image/heif` type, before reading the body), and the Studio explains in French to export or share the photo as JPEG (or PNG), or to set the camera to its most compatible (JPEG) format. The Studio recognizes HEIC files by type or extension before uploading.
- Limits: 5 MiB upload (read through a limit; larger input is rejected, not truncated), 4096 px per side, 16 megapixels. Dimensions are checked from the header before the full decode (decompression-bomb defence); the full decode must then succeed and match the header. Within these limits one decode could allocate about 430 MB (progressive CMYK; see the correction below), which did not fit the EXAMPLE `LEARNOO_APP_MEMORY=512m`. **Correction (issue 42 review, 2026-11-25):** the earlier figure of about 250 MB per decode (and 500 MB for two) did not cover CMYK JPEGs, and before production the maintainer had to choose between more memory, one decode at a time, or refusing CMYK. **Resolution (2026-11-26, [measurements](measurements/upload-memory.md)):** generated worst-case inputs (no downloaded files) were measured per `Process` call and against the real server under 4 concurrent uploads plus readers, also in a container limited to 512 MiB, where the previous code was OOM-killed within seconds. Changes: (1) CMYK and YCCK (four-component) JPEGs are refused before decoding with `ErrUnsupportedCMYK` (also `ErrUnsupportedType`; API `415 unsupported_cmyk`, French explanation in the Studio): phones and screenshots never produce them, Go converts their colours without the profile, and they were the most expensive variant (about 450 MB allocated). (2) Before the full decode, `Process` estimates from the headers the bytes the decoder and the orientation step allocate for large buffers (`internal/media/cost.go`: pixels padded to whole MCUs, 4 bytes per sample for progressive JPEG coefficients, the RGBA conversion of JPEGs stored as RGB, the rotated copy; for PNG 1, 4 or 8 bytes per pixel, doubled for Adam7 interlacing; for WebP the decoded and transformed pixels, the alpha plane and, for every lossless stream (VP8L, or lossless-compressed alpha), a fixed bound of about 140 MiB for the up to 2600 Huffman groups of `golang.org/x/image/vp8l`, which do not depend on the image size; review finding of 2026-11-26, the line-by-line derivation is in `cost.go`) and refuses images above `MaxDecodeBytes` = 192 MiB with `ErrTooComplex` (API `422 image_too_complex`). The estimate is the sum of these allocations, not their peak, so it holds even when the collector has not yet freed earlier buffers; a test checks it against the measured heap for every worst-case input. The Huffman tables' per-tree temporaries are released before the next tree is read and are counted once rather than summed. Refused in practice: progressive JPEGs without chroma subsampling above about 13 megapixels (about 10 with EXIF rotation), progressive RGB JPEGs above about 10 megapixels, interlaced 16-bit PNGs above about 12 megapixels, lossless WebP above about 7 megapixels and WebP with lossless-compressed alpha above about 5 (export as PNG instead). Accepted at the full 16 megapixels: baseline JPEGs of any subsampling with rotation (phone photos: about 85 MiB), progressive 4:2:0 JPEGs with rotation (about 175 MiB), 8- and 16-bit PNGs, lossy WebP without alpha (subject to the stored-size limit below). (3) The re-encoded image is limited to `MaxEncodedBytes` = 16 MiB (`ErrTooComplex` above), which bounds the output buffer (at most about 48 MiB while a `bytes.Buffer` grows); the finished asset keeps an exact-size copy when the buffer has more than 1/8 spare capacity, and `Store.Put` compares an existing file with the new bytes in 32 KiB chunks instead of reading it whole. (4) `MaxConcurrentDecodes` = 1: with the EXAMPLE limit of one CPU, a second concurrent decode is not faster, and one decode keeps the bound simple. Further callers wait for the slot or stop when their context ends. (5) `serve` sets `GOMEMLIMIT` to three quarters of the container's cgroup memory limit unless `GOMEMLIMIT` is set ([DEPLOYMENT.md](DEPLOYMENT.md#app-memory)); without it the collector let the heap reach about twice the live heap. Computed budget: one decode (at most 192 MiB) + its output buffer (at most 48 MiB) + its upload body (5 MiB, about twice that while `io.ReadAll` grows) + the three other upload slots, each holding a body or a finished asset (at most 16 MiB each) + an idle server heap of about 20 MiB, about 320 MiB, below the 384 MiB `GOMEMLIMIT` of a 512 MiB container; 512 MiB stays an EXAMPLE value, now with a measured minimum. The orientation step got a direct path for RGB-stored JPEGs (the CMYK path was removed with CMYK support). Reading the upload happens before the decode slot is taken, so the API slice still bounds request bodies and concurrent uploads.
- Re-encoding: the decoded pixels are always re-encoded, so stored bytes carry no EXIF/GPS, XMP, text chunks or ICC profiles. PNG is stored as PNG and JPEG as JPEG at fixed quality 90. Go's standard library cannot encode WebP, so WebP is decoded with `golang.org/x/image/webp` and stored as lossless PNG with `content_type` `image/png`.
- Known limitations: dropping ICC profiles may shift colours slightly in wide-gamut images. Go's JPEG encoder always uses 4:2:0 chroma subsampling, so fine coloured detail (for example red text on a diagram) can blur; diagrams should be uploaded as PNG. Re-encoding is not idempotent for JPEG: processing a stored JPEG again can yield different bytes (seen with noisy images) and so a new asset. WebP stored as PNG can be larger than the upload. Strict end-of-file checks rejected JPEGs that carry anything after the end-of-image marker: multi-picture (MPF) previews, Android Ultra HDR gain maps, motion-photo video, or zero padding. **Maintainer decision (2026-11-24):** this strict rejection was kept for the technical pilot, with a clear explanation to the author; validation is not weakened to accept these files. Issue 42 since accepts those structures only after structural validation (see "Phone photos" above) and applies EXIF orientation; other trailing data is still refused with `ErrTrailingData`, which the upload API maps to an understandable message. "Rejects polyglots" means trailing data after the final PNG chunk, JPEG end-of-image marker or RIFF length. A payload hidden inside an ancillary PNG chunk or JPEG/WebP metadata segment is accepted at upload but never stored, because re-encoding drops it.
- Storage: content-addressed and immutable. The key is `<sha256>.<png|jpg>`, where the SHA-256 is of the stored (re-encoded) bytes, at `ab/cd/<key>` under the media directory. Only assets returned by `Process` can be stored, and their bytes are rechecked against the hash and content type. Files are written to a temporary file in the same directory, fsynced, made read-only (0444) and hard-linked into place, then the shard directories are fsynced; an existing key is never overwritten. Identical concurrent writes are idempotent and a different file under an existing key is reported as a conflict. The media volume must therefore support hard links. Directories are created 0750. Keys are validated against `^[0-9a-f]{64}\.(png|jpg)$` and all access goes through `os.Root`, so no key can reach outside the directory. A crash can leave `.tmp-*` files; they never match a key, so they are never served, and they may be deleted.
- Replacing an image means uploading a new asset. Uploads whose canonical bytes are identical have the same SHA-256 and therefore the same file. The persistence slice plans a unique `sha256` column, so such uploads would share one asset row; that is safe because assets never change.

## Studio API (LRN-006)

Implementer choices for the HTTP slice on 2026-11-24 (`internal/studioapi`, contract in [API.md](API.md#studio-lesson-drafts-and-media-lrn-006)):

- **Authorization order.** Session (401), then CSRF on unsafe methods (403), then the `author` permission through `permissions.Middleware` (403) before any ID is parsed or looked up; lesson writes recheck it in their transaction. A missing `author` permission therefore says nothing about which IDs exist.
- **Reads.** A revision can be read only by its author, in any status. Other authors get the same `404 not_found` body as for a missing ID, and the same holds for saving, submitting and discarding someone else's draft, so revision IDs cannot be probed. Reviewer access belongs to LRN-007 and reader access to LRN-008. Only a lesson's owner may start a draft or a translation of it (see "Lesson ownership" under Lesson persistence); for anyone else `POST /api/lessons/{id}/drafts` returns the same `404 not_found` as for an unknown lesson, and `translationOf` the same `422 unknown_lesson`, so lesson IDs cannot be probed through these endpoints.
- **Identifiers.** Numeric database IDs for lessons, revisions, subjects, chapters and media; the lesson's random `public_id` is kept for public URLs (LRN-008). Title, objectives and language are read from the schema v1 document and are not separate request fields.
- **Raw-body upload.** `POST /api/media` takes the image as the raw body with its image `Content-Type`, not multipart: one file per request, no filename (never trusted anyway), no multipart parser or temporary files, and the body is bounded by `http.MaxBytesReader` at 5 MiB. A declared larger `Content-Length` is refused before reading. Only `image/png`, `image/jpeg` and `image/webp` are accepted as declared types; `media.Process` then checks the bytes.
- **Upload concurrency.** At most 4 uploads per process read or process a body at once (about 20 MiB of bodies), on top of `media.MaxConcurrentDecodes` (2 decodes; 1 since the 2026-11-26 memory resolution under Media upload limits). Further uploads wait up to 5 seconds without reading their body, then get `503 busy` with `Retry-After`. Slots are per process, not per user: one author (or a few slow connections) can occupy all of them for up to the read timeout; per-user limits belong with deployment rate limiting (LRN-010/LRN-022). Slow clients are bounded by the server's 15-second read timeout; a body that does not arrive in time gets `408 upload_timeout` (no `Retry-After`, since retrying the same connection immediately would not help). Deployment may revisit the timeout for slow connections.
- **Media rows and access.** The file is stored before its `media_assets` row, so a row never names a missing file. Identical canonical bytes (same SHA-256) reuse the existing row (`ON CONFLICT DO NOTHING`: a concurrent identical upload can hit the unique storage key before the unique hash); its `created_by` stays the first uploader. Every successful upload, new or deduplicated, also records the caller in `media_uploads` (migration `0005`) in the same transaction, after the in-transaction `author` recheck. The response is `201` in both cases, so the status does not reveal whether someone else uploaded the same image; media IDs are sequential, so deduplication remains observable only through the returned ID. Files left without a row (a failure or revocation between the two steps) are never served; a cleanup job is pending.
- **Media serving.** Object-scoped: a signed-in `author` may read an asset only if they uploaded it (a `media_uploads` link) or authored a revision that references it; anyone else gets the same 404 as for a missing ID. Drafts may reference only assets their author can read (`422 unknown_media` otherwise, as for a missing ID), so referencing cannot be used to gain access. That check runs just before the lessons transaction rather than inside it: links are never removed, and the only way access shrinks is the caller discarding their own draft, so the gap is harmless. Reviewers read the media of revisions in review in their subjects through a separate route (LRN-007, [Review and publication](#review-and-publication-lrn-007)); student/reader access comes with LRN-008. The content type comes from the validated storage key, never from the request; responses carry `X-Content-Type-Options: nosniff`, `Content-Security-Policy: default-src 'none'; frame-ancestors 'none'; sandbox`, `Content-Disposition: inline`, `Cache-Control: private, no-store` and `Vary: Cookie`. IDs must be positive decimal integers; rows whose key is not a valid store key are never served.
- **Error codes.** Stable codes per persistence error (API.md table). `ErrTrailingData` maps to `422 trailing_data` with a message telling authors to re-export the image or upload PNG (data that is not a recognized phone-photo structure). `ErrUnsupportedHEIC`, and a declared `image/heic` or `image/heif` type, map to `415 unsupported_heic` with guidance to export the photo as JPEG or PNG (issue 42).
- **Retryable conflicts.** PostgreSQL deadlock (`40P01`) and serialization (`40001`) failures, on lesson writes and media rows, return `409 retry`: the transaction rolled back, nothing was written, and the client may resend the same request. 409 rather than 503 because the cause is a concurrent edit, not server load.
- **Configuration.** `serve` requires `LEARNOO_MEDIA_DIR` as an absolute path, with no default, so uploads never fall back to the working directory or repository.
- **Strict request bodies.** Studio JSON bodies must be exactly one object; its top-level keys are matched case-sensitively and may appear once (scanned with `json.Decoder.Token` before decoding, because `encoding/json` matches keys case-insensitively and keeps the last duplicate). The nested `content` document is checked by the schema v1 decoder (`internal/strictjson`), which refuses case-folded and duplicate keys at every level (`422 invalid_content`); the lessons store keeps only the canonical re-encoding of what that decoder read, and submission rechecks that the stored content is canonical, so what is stored, reviewed and rendered is always exactly what was validated. NUL characters are rejected before the database with a plain `invalid_content` message, and validator messages never name Go types. The login decoder applies the same exact-key rules through `internal/strictjson`.
- **Null and integer rules (issue 51).** The Studio decoder refuses `null` for every field except nullable pointers (such as `chapterId`, `translationOf`) and types that decode JSON themselves (which then own their null handling; no LRN-006 request field uses one); `api:"nonnull"` marks a pointer kept only to detect a missing key (`expectedVersion`). Integer fields take only integer literals, and errors name JSON keys only. This uses the issue's alternative, Studio-specific checks in `internal/studioapi/decode.go`, rather than extending `internal/strictjson`: strictjson treats every pointer as nullable (so it cannot express a required non-null `expectedVersion`), its messages name Go types, and it is shared with the lesson schema and login decoders. The rules cover top-level values only, so the decoder admits only request types whose fields are scalars, pointers to scalars, arrays of scalars, `json.RawMessage` or types with their own `UnmarshalJSON`, with unique JSON names and only untagged, non-pointer embedded structs; any other request type panics on first use, and a test checks every request type and its allowed keys.
- **Failed permission checks are not denials.** `permissions.RequireTx` joins `ErrDenied` with the database error that prevented the check; the API reports such errors as `500 internal` (logged without request data), or `409 retry` for deadlocks and serialization failures, rather than as `403`/`404`. (`permissions.Middleware` still answers `403` when its own lookup fails, as specified in LRN-005.)

## Review and publication (LRN-007)

Implementer choices on 2026-11-24 within the execution contract on issue 7 (`internal/review`, `migrations/0006_review_publication.sql`, HTTP contract in [API.md](API.md#review-and-publication-lrn-007)). Items marked **open question** are product decisions left to the maintainer; the implementation takes the conservative reading noted and changes nothing else.

- **Tables.** `review_decisions` (revision, reviewer, action `approve` or `request_changes`, comment, `decided_at`) and `publication_audit` (lesson, revision, previous published revision, actor, action `publish`, `occurred_at`, `xact_id`). Both are append-only: update, delete and truncate are rejected by `zz_guard_*` triggers (SQLSTATE `LRN01`). Times are the transaction time, enforced by the insert guards, so rows cannot be backdated. A change request needs a non-blank comment (check constraint); comments are trimmed, at most 5000 characters, and an approval without comment stores `NULL`.
- **Decision and status stay consistent in the database.** A revision leaves `in_review` only together with its decision: an update guard on `lesson_revisions` requires a `review_decisions` row with the matching action, and a deferred constraint trigger requires every decision to have moved its revision to the matching status by commit. One decision per revision (unique `revision_id`) and the decision insert guard accepts only a revision in review, locked `FOR UPDATE` after its lesson (`FOR SHARE`), so of two concurrent decisions exactly one applies; the other gets `409 not_in_review`. The guard also rejects a reviewer who authored the revision (administrators included) and a reviewer without an active assignment for the revision's subject (assignment and account rows share-locked), so self-approval and unassigned decisions are refused even when the application is bypassed. Existing LRN-006 tests that simulated decisions with a bare status `UPDATE` now insert a decision in the same transaction; their assertions are unchanged.
- **Publication and audit stay consistent in the database.** The audit insert guard locks the lesson `FOR UPDATE`, requires `previous_revision_id` to equal the current pointer, the revision to be an approved revision of that lesson (share-locked) and the actor to be an active `publisher`; a deferred trigger requires the pointer to name the audited revision by commit. Setting the pointer to a revision requires an audit row of the same transaction recording exactly that change (`xact_id` is the writer's top-level `pg_current_xact_id()`, forced by the insert guard), so an audit row of an earlier transaction cannot be reused. Clearing the pointer (unpublication) is LRN-009 and is not guarded yet; LRN-009 should extend the audit actions and require an audit row for every pointer change. The database does not check the base revision or that the revision was never published, so LRN-009 restoration can reuse this table with its own action; the store checks both. *Since LRN-009 every pointer change, including to NULL, needs an audit row, and the database also checks the base and never-published rules for `publish` ([LRN-009](#withdrawal-unpublication-and-restoration-lrn-009)).*
- **Guard conventions.** Every new function pins `search_path = pg_catalog, pg_temp` and reaches other tables through `TG_TABLE_SCHEMA` with bound parameters, and none is `SECURITY DEFINER`. A database test runs each guard as a non-owner role on fresh connections with temporary shadow tables (`lesson_revisions`, `lessons`, `review_decisions`, `publication_audit`, `reviewer_assignments`, `user_permissions`, `users`) and checks they are ignored; reverting the qualification makes it fail. Like the LRN-006 guards, these bind only a role that neither owns the tables nor is a superuser. The runtime role needs `UPDATE` on `reviewer_assignments`, `user_permissions` and `users` for the share locks (as `permissions.RequireTx` already does).
- **Store.** `review.Store` `Approve`, `RequestChanges`, `Publish`, `ReviewRevision` and `ReviewQueue`. Decisions lock the lesson `FOR SHARE`, then the revision `FOR UPDATE`, then check `permissions.RequireReviewerTx` for the revision's subject (LRN-005), then self-review, then status. Publication checks `permissions.RequireTx(publisher)` first, then locks the lesson `FOR UPDATE` and the revision `FOR SHARE`, and requires: approved; never published (`candidate_closed_at` NULL and not the current pointer, else `already_published`); lesson not archived; the revision's `base_revision_id` equal to the current pointer (else `stale_base`, nothing written). Audit insert and pointer update follow in the same transaction; the existing trigger closes the candidate. Lock order stays lesson, then revision.
- **Base comparison.** The expected base is the revision's own `base_revision_id`, recorded under the lesson lock when its draft was created; the publish request carries no client-side base (body `{}`). A publisher who publishes an author's revision therefore cannot overwrite a newer publication, and a revision whose draft predates the current pointer is refused.
- **Publisher may be the author.** Publishing is a separate permission and does not require a different person from the author once another reviewer approved (CONTENT_AND_EDITORIAL.md says only that authors cannot approve their own work). Tested explicitly.
- **Reviewer access.** Reviewers read revisions in review in their subjects (`GET /api/review/revisions/{id}`) and the media they reference (`GET /api/review/media/{id}`); anything else is the same `404` as a missing ID. A reviewer may read their own submitted revision (they could already as its author) but it is excluded from their queue and they cannot decide on it. Routes first require at least one reviewer assignment (`permissions.Middleware.RequireAnyReviewer`, 403), then check the subject in the transaction. Decided revisions leave the reviewer's view.
- **Queue.** In-review revisions of the caller's assigned subjects, optionally one subject, oldest submission first, capped at 200 with no pagination (dashboards are M2).
- **Attribution.** Every revision response carries `authorId`, the decision (`review`: action, reviewer, comment, time) and `approvedBy`. The author sees the change-request comment as feedback.
- **HTTP.** Review routes under `/api/review/…`; publication is `POST /api/revisions/{id}/publish`. Strict JSON as for the Studio API. On review routes a denial (including a revocation racing the request) is `404`, indistinguishable from a missing revision; on publication it is `403`, because `publisher` is global and reveals nothing about subjects. New codes: `403 self_review`, `409 not_in_review | not_approved | already_published | stale_base`, `422 comment_required | invalid_comment`.
- **Open question: reviewer identity on change requests.** Lessons display reviewer credit (CAHIER_DES_CHARGES.md §2.2), so the approving reviewer is exposed. Whether the author should also see who requested changes is not decided; the API currently returns `reviewerId` for both actions. *LMS working default (2026-11-26): authors see reviewer identity and feedback ([LMS_PRODUCT_SPEC.md §8](LMS_PRODUCT_SPEC.md#8-reviewer-publisher-and-administrator-experiences)).*
- **Submission audit (settled 2026-11-26).** The clarified gap is closed: every submission writes an immutable audit row in the same transaction; see [Submission audit](#submission-audit).
- **Open question: archived lessons.** Publication of a revision of an archived lesson is refused (`409 archived`); decisions on revisions of archived lessons are allowed. Archival has no code path yet, so neither choice is exercised outside tests. *LMS working default (2026-11-26): see [LMS_PRODUCT_SPEC.md §4](LMS_PRODUCT_SPEC.md#delete-archive-and-restore).*
- **Open question: publisher visibility.** Publishers have no endpoint to list or read approved revisions awaiting publication; they need the revision ID from elsewhere. A publisher queue or read access was not in the contract. *Addressed by issue #66 (second slice): `GET /api/publish/queue` and `GET /api/publish/revisions/{id}`.*
- **Unchanged open question.** A stale approved candidate (its base no longer the pointer) cannot be published and keeps blocking new drafts ([Lesson persistence](#lesson-persistence-lrn-006)); LRN-007 implements only the refusal. *LMS working default (2026-11-26): audited administrator withdrawal, then a fresh draft and review ([LMS_PRODUCT_SPEC.md §5](LMS_PRODUCT_SPEC.md#restoration-and-audit)).*

## Withdrawal, unpublication and restoration (LRN-009)

Implementer choices on 2026-11-24 within the execution contract on issue 9 (`internal/review/withdraw.go`, `internal/studioapi/withdraw.go`, `migrations/0007_withdrawal_restoration.sql`; HTTP contract in [API.md](API.md#withdrawal-unpublication-and-restoration-lrn-009)). Items marked **open question** are product decisions left to the maintainer; the implementation takes the conservative reading noted and changes nothing else.

- **0006 extended, not edited.** `0006`'s reviewed history is kept: `0007` alters `publication_audit` and replaces two of its functions with `CREATE OR REPLACE` (their triggers stay). Editing `0006` would have been marginally shorter but would rewrite a migration other branches already build on.
- **One pointer audit.** `publication_audit` records every change of `lessons.published_revision_id` with action `publish`, `restore` or `unpublish`. `revision_id` is the new pointer (NULL only for `unpublish`), `previous_revision_id` the replaced one (required for `unpublish`); a non-blank `reason` of at most 2000 characters is required for `unpublish` and forbidden otherwise (check constraints). The existing rules still apply to every row: transaction time and `xact_id` forced, the lesson locked `FOR UPDATE`, `previous_revision_id` equal to the current pointer, and a deferred check that the pointer names `revision_id` (NULL included) at commit. Consequently a transaction makes at most one pointer change per lesson.
- **Every pointer change is audited, including to NULL.** The pointer guard on `lessons` now requires, for any change (and for an INSERT with a non-NULL pointer), an audit row of the same transaction with exactly that lesson, new pointer and previous pointer. This closes the LRN-007 review note: a direct-SQL writer can no longer unpublish silently, and a republication's audit row cannot claim a false previous pointer.
- **Database rules per action.** `publish`: an approved revision of the lesson, never published (`candidate_closed_at` NULL), not withdrawn, whose `base_revision_id` equals the current pointer, by an active `publisher`. The base and never-published rules were store-only in LRN-007; they are now also enforced in the database, so a stale-base republication through direct SQL is refused. `restore`: an approved, non-withdrawn revision of the lesson with an earlier `publish` row, by an active `publisher` or `administrator`; no base check. `unpublish`: by an active `administrator`. Existing LRN-006/LRN-007 tests that simulated unpublication with a bare pointer update, or restoration with a `publish` row, now write the corresponding `unpublish` (with a simulated administrator) or `restore` row; their assertions are unchanged.
- **"Was published" test.** A revision was published if a `publish` audit row names it. `candidate_closed_at` cannot answer this, because withdrawal of a pending candidate sets it too. The audit is append-only and its rows are only accepted together with the pointer change, so the test is reliable for every role bound by the guards.
- **Withdrawal.** `revision_withdrawals` (lesson, revision unique, administrator, reason non-blank ≤ 2000 characters, transaction time, `xact_id`), append-only. Its insert guard locks the lesson `FOR UPDATE`, requires an approved revision of that lesson (share-locked) and an active `administrator`. A withdrawn revision can never be named by the pointer: the audit insert guard refuses `publish` and `restore` of it, a `zz_guard_` trigger on `lessons` refuses the pointer, and a deferred check on the withdrawal refuses to commit while the lesson still points at it, so withdrawing the published revision must unpublish it in the same transaction (the store writes the `unpublish` row with the withdrawal's reason). A revision is withdrawn at most once; withdrawal is final and has no undo.
- **Only approved revisions are withdrawn.** Drafts are discarded, revisions in review are decided, and `changes_requested` revisions can never be published; withdrawal therefore applies to approved revisions only (`409 not_approved` otherwise). Implementer reading.
- **Releasing a pending candidate.** An AFTER INSERT trigger on `revision_withdrawals` sets `candidate_closed_at` of the withdrawn revision if still NULL. Its function is `SECURITY DEFINER`, owned by the table owner, pins `search_path = pg_catalog, pg_temp`, names `lesson_revisions` through `TG_TABLE_SCHEMA`, refuses to run unless fired AFTER INSERT FOR EACH ROW on the owner's permanent `revision_withdrawals`, and has `EXECUTE` revoked from PUBLIC, like `lessons_close_published_candidate`. `lesson_revisions_guard_update` already accepts that close only from an owner-run trigger at depth ≥ 2, so it is unchanged. Lock order stays lesson, then revision. Tests show a non-owner role cannot attach the function to its own table (`42501`), its own trigger cannot close a candidate, the owner cannot fire it from a temporary table, and a legitimate withdrawal by the non-owner role closes the candidate at the transaction time.
- **Expected current pointer.** Withdrawal, unpublication and restoration each carry the pointer the caller expects (`expectedPublishedRevisionId`, `null` allowed except for unpublication). The store compares it under the lesson row lock; a mismatch is `ErrStalePointer` (`409 stale_pointer`) and nothing is written. Withdrawal carries it even when the withdrawn revision is not published, so a withdrawal never acts on a lesson state the administrator did not see.
- **Restoration eligibility.** Restoration rechecks, in the transaction: approved, same lesson (via the revision), never withdrawn, previously published, lesson not archived, content valid and canonical under the current schema v1 validator (the same check as submission, `lessons.CheckStoredContentTx`), and every `revision_media` reference resolving to an asset. Media assets are immutable and never deleted, so the media check cannot fail today except on a damaged database; there is no media withdrawal state. The historical base check is not applied (CONTENT_AND_EDITORIAL.md). Restoring the current revision is `409 already_current`.
- **Permissions.** Withdrawal and unpublication: `administrator` (CAHIER_DES_CHARGES §2 table). Restoration: `publisher` or `administrator`, checked with the new `permissions.RequireAnyTx` (grant and account rows share-locked) and `Middleware.RequireAny`. Disabled accounts and revocations committed before the in-transaction check are denied.
- **Concurrency.** Every path locks the lesson row `FOR UPDATE` before reading the pointer, so at READ COMMITTED (the store's level) publication, restoration, withdrawal and unpublication of one lesson are applied one at a time, and each guard statement after the lock sees the previous one's committed rows. Tests on PostgreSQL: restoration racing publication (one applies; the other gets `stale_pointer` or `stale_base`; one new audit row), withdrawal racing publication of the same revision (either withdrawn and never published, or published with the withdrawal refused as stale), concurrent restorations (exactly one).
- **Stale snapshots (independent review finding, fixed).** A withdrawal only inserted a row and locked the lesson; a direct-SQL writer at REPEATABLE READ or SERIALIZABLE whose snapshot predated a committed withdrawal could still restore the withdrawn revision, because the guards read with that snapshot and nothing it then locked or updated had changed. Every withdrawal now also increments `lessons.withdrawal_count` (by the same owner-run `SECURITY DEFINER` trigger, lesson row before revision; a `zz_guard_` trigger accepts the change only from an owner-run trigger, by one, alone, and requires 0 on insert). Since every pointer change locks and updates the lesson row, such a writer now fails with `40001`. Regression tests run restoration and publication of a revision withdrawn after the writer's snapshot, at REPEATABLE READ and SERIALIZABLE, as the store's role and as a non-owner role: refused, pointer unchanged.
- **Audit of the other guards (0004–0007) for insert-only facts read under an old snapshot.** Each is either conflict-protected or fail-safe: review decisions (the decision guard locks the revision `FOR UPDATE`, and a concurrent decision updates its status, so a stale writer gets `40001`; the unique `revision_id` also applies); grants and reviewer assignments (a grant inserted after the snapshot is invisible, which denies; revocation deletes and disablement updates the share-locked rows, which conflict); `publish` rows for the was-published test (an invisible row refuses restoration); the never-published and base rules (read from rows locked after the lesson, whose concurrent changes update the lesson row); the draft base check (a stale base only yields a draft that publication refuses, and the revision-number trigger updates the lesson row, which conflicts); the commit-time checks on `review_decisions`, `publication_audit` and `revision_withdrawals` (they read rows the transaction has locked or written itself). `media_uploads` (0005) is read by application queries, not guards.
- **Guard conventions and verification.** As in 0004/0006: `zz_guard_*` names, SQLSTATE `LRN01`, pinned `search_path`, `TG_TABLE_SCHEMA`-qualified references. A non-owner role on fresh connections with temporary shadow tables (`lessons`, `lesson_revisions`, `publication_audit`, `revision_withdrawals`, `user_permissions`, `users`) is refused by every new guard. Mutation checks were run by hand on the key guards (unaudited NULL pointer, unqualified/unpinned lookups, missing withdrawn checks, missing commit-time check, close trigger without firing-table check, without `SECURITY DEFINER` or with `EXECUTE` left to PUBLIC, missing was-published and never-published checks, withdrawal by a non-administrator, a withdrawal that does not update the lesson row, an unguarded `withdrawal_count`); each mutation made at least one test fail. The threat model is unchanged: these guards bind a role that neither owns the tables nor is a superuser.
- **Open question: which revisions can be restored.** CONTENT_AND_EDITORIAL.md allows restoring "a previously approved, non-withdrawn revision" without the base check. Read literally, that lets restoration publish a pending approved candidate while skipping the publication base check. The implementation restricts restoration to revisions that were published before (conservative reading, enforced in the store and the database); never-published approved revisions go through publication. Whether the broader reading is intended is not decided.
- **Open question: stale approved candidates after unpublication or restoration.** If the lesson is unpublished or restored while an approved candidate is pending, the candidate's base no longer matches the pointer: publication refuses it (`stale_base`), restoration refuses it (`never_published`), and it keeps blocking new drafts until an administrator withdraws it. No automatic behaviour (release, rejection of the unpublication/restoration, or forced withdrawal) is added; which is intended is not decided.
- **Not included.** Administration pages (LRN-019), listing endpoints for the pointer audit and withdrawals (the store has `PointerHistory` and `Withdrawals`, unexposed), notifications, deployment.

## Student reader (LRN-008)

Implementer choices on 2026-11-24 within the execution contract on issue 8 (`internal/reader`, `internal/invitations`, `migrations/0008_reader.sql`, routes in [API.md](API.md#student-reader-lrn-008)). Items marked **open question** are left to the maintainer.

- **Release gate: privacy.** The privacy, deletion and retention policy is still open (see [Open decisions](#open-decisions)). The implementation collects only the invited email, the display name the student chooses and the password hash; no age, school, section or consent field. Invitation rows (email, operator label, times) and their audit rows are kept indefinitely and cannot be deleted by the application role; bookmarks are deleted with their account. **Inviting real students waits for that policy and for LRN-011.** Until then only simulated addresses are used.
- **Invitations.** A 256-bit random token per invitation; only a domain-separated SHA-256 is stored (`student_invitations.token_hash`). Default lifetime 72 hours, operator choice 1 hour to 30 days (also a database constraint). Single use is enforced twice: the store locks the invitation row (`FOR UPDATE`, so of concurrent acceptances exactly one creates the account) and a database guard allows exactly one change to a row, acceptance, at the transaction time, before expiry, by an account with the invited email; nothing else changes and rows are never deleted or truncated. Issue and acceptance are written to the append-only `student_invitation_audit` by triggers, so the application cannot skip them. An email that already has an account is refused when issuing and when accepting. Several pending invitations for one email are allowed; the unique account email still yields one account. Unknown, malformed, expired and used tokens get one message.
- **Operator label.** `invite-student` records `<os user>@<hostname>` (self-asserted, not authentication), built by `permissions.LocalOperatorLabel()` (see "Operator trust boundary") and revalidated by `invitations.Issue` with the same rules as permission and account status audit labels (1 to 200 characters, trimmed, no control, format or line/paragraph separator characters, so a label cannot hide or reorder text); the `student_invitations` constraint uses the same locale-independent code-point list as migrations 0002 and 0003. Invitations are never created over HTTP.
- **Acceptance.** The invited person sets a display name (1 to 100 characters, trimmed; control and bidirectional formatting characters are refused because names appear in credit lines) and a password (at least 12 characters and at most 1024 bytes, as `create-user`, typed twice), hashed with the service's Argon2id parameters. The new Student holds no permission and is signed in through the normal login service (same throttle and session rotation).
- **Throttling.** Invitation page views and submissions share the login throttle table under their own key scope: more than 20 per client address per 15 minutes return 429. Viewing counts as well, because it checks a token. Unlike login, a successful acceptance does not clear the counter, so one address allows about 10 activations per 15 minutes (each typically costs a page view and a submission, more after validation errors). **Pilot preparation note (LRN-011):** students activating from one school or home network behind NAT share that budget; stagger activations or raise `InvitationLimit` before a group session.
- **Sign-in page.** `GET/POST /login` is a plain HTML form (no JavaScript) calling the same `auth.Service.Login` as the JSON API. Login CSRF is covered by Go's cross-origin protection, as for the API. The post-login `next` target is limited to `/learn` paths of plain segments to prevent open redirects. Password recovery stays out of scope.
- **What students may read.** One SQL view, `reader_published_lessons`, defines it: a non-archived lesson whose published pointer names an approved, non-withdrawn revision of that lesson. Drafts, revisions in review, approved but unpublished revisions, unpublished lessons, withdrawn revisions and archived lessons never appear in navigation, search, lesson pages or new bookmarks. LRN-009 (migration 0007) already guarantees that the pointer never names a withdrawn revision; the view repeats the exclusion (`NOT EXISTS` on `revision_withdrawals`) as defence in depth. Unpublication, restoration and withdrawal take effect for students on their next request, since the reader keeps no copy; any future change to what counts as published must update this view. The reader has no other publication logic. Archived lessons are hidden although archival has no code path yet.
- **Rendering.** The lesson body is `rendering.RenderBlocks` of the published snapshot, the same node templates the preview page uses (`Render` now calls the shared `blocks` template; its output is byte-identical). The page sets `lang`/`dir` on the title, objective and article from the lesson language (`ar` is `rtl`); blocks keep their own `lang`/`dir`, and formulas stay LTR. The interface is French and independent of the lesson language (Arabic interface: LRN-023). The schema v1 `status: "unreviewed"` field is not shown on published lessons, and the reader adds no "unreviewed" chip; all content on this branch is TEST material. **Open question:** whether a schema field or notice should mark pilot content that is published but not teacher-validated.
- **Credit.** "Rédigé par" the published revision's author and "Relu et approuvé par" the reviewer of its approve decision, by current display name, escaped. Names are shown even if the account was later disabled. Richer profiles are LRN-021.
- **Navigation.** Subjects and chapters have no names or ordering yet (LRN-014), so pages show their codes; chapters sort by code with lessons without a chapter last ("Sans chapitre"); lessons sort by folded title. The chapter is the published revision's, so it follows republication. Previous/next links and error reports (LRN-015) are not built. *Error reports: see [Error reports](#error-reports-lrn-015). Names and order: since issue #86 pages show catalogue display names (code as fallback) and sort subjects and chapters by display order, then code; see [Catalogue names and order](#catalogue-names-and-order-issue-86).*
- **Bookmarks.** Keyed by lesson (addressed by its random `public_id`), so they survive new revisions and title changes. Only currently published lessons can be bookmarked; a bookmark of a lesson that later stops being published stays, listed as unavailable without a title, and can be removed. At most 500 per user, checked before insert; concurrent adds can exceed it by a few rows.
- **Search.** See [API.md](API.md#title-search): substring match on folded titles (`reader_fold`), bound parameter with `strpos` (no `LIKE` patterns), 2 to 100 characters, 50 results, no trigram index (needs the `pg_trgm` extension; revisit before public launch). The query travels in the URL (`GET /learn/search?q=`) so results can be reloaded; the server does not log URLs and sends `Referrer-Policy: same-origin`.
- **Caching and assets.** Every response from a reader route, static files included, sends `Cache-Control: private, no-store` and `Vary: Cookie`; responses produced before a reader route is reached (cross-origin rejection, and the JSON 404 catch-all for unknown paths and unsupported methods on reader paths) keep the server-wide `no-store`, which `internal/server` was left unchanged for (its login tests assert exactly `no-store`). Consequently KaTeX (about 360 KiB) was fetched again for each lesson. *Superseded for pages' assets by [Fingerprinted static assets](#fingerprinted-static-assets-issue-88): pages now load them from cacheable `/assets/` URLs; the unversioned `/static/` files keep this rule.* Generic CSS/JS and KaTeX are public; lesson media (today only the renderer's fixture image) needs a session. Header tests do not prove the live CDN configuration.
- **Browser tests.** `npm run test:reader` uses a separate Playwright configuration because it needs PostgreSQL; its server is a Go test helper that seeds TEST lessons in an isolated schema. CI runs it after `test:browser`. It covers a 360 px viewport in desktop Chromium; physical-phone and throttled-network checks remain human items on issue 4.
- **Open question: invitation management.** There is no command to list or revoke pending invitations; an unwanted link stays valid until it expires (at most 30 days, 72 hours by default).

## Error reports (LRN-015)

Implementer choices on 2026-11-24 within issue 45 (`internal/reports`, `internal/studioapi/reports.go`, the reader form in `internal/reader`, `migrations/0009_error_reports.sql`, renumbered at merge; routes in [API.md](API.md#error-reports-lrn-015)). Items marked **open question** or **to confirm** are left to the maintainer.

- **Release gate: privacy.** A report stores the reporting account and free text the student wrote, which may contain personal data despite the form's guidance. The privacy, deletion and retention policy is still open (see [Open decisions](#open-decisions)). Reports and resolutions are kept indefinitely: the application role cannot delete or truncate them (database guards), and an account or lesson with reports cannot be deleted (foreign keys). **Collecting reports from real students waits for that policy**, as LRN-008's invitations do; until then only simulated accounts and TEST lessons are used. The policy must say how long report text is kept, whether it is redacted or deleted when resolved or when the account is deleted, and who may read it.
- **Who may report.** Any signed-in, active account, as the CAHIER §2.2 matrix grants "report an error" to students, teachers, reviewers and administrators; the reader needs no permission. Anonymous reports are refused (401). The issue's "only authenticated students" is read as "only authenticated readers". **To confirm.**
- **Who handles reports.** Reviewers of the lesson's subject (active assignment, the lesson's immutable subject) and administrators (all subjects, with or without an assignment), as in CAHIER §2.2 ("Handle error reports … own subjects / ✓"). Resolving a report is not an editorial decision, so the rule that administrators review content only in assigned subjects does not apply. Students, authors and publishers without either get `403` before any lookup (`permissions.Middleware.RequireReviewerOrAny`, new and additive); a reviewer of another subject gets the same `404` as for a missing report.
- **The revision shown.** The lesson page sends back the published revision's lesson-scoped number (not its sequential database ID). The store share-locks the lesson row, reads the current published revision through `reader_published_lessons` and refuses a mismatch (`ErrRevisionChanged`, `409` page showing the current revision with the text kept). The insert guard repeats the rule in the database: it share-locks the lesson and requires a non-archived lesson whose pointer names the reported revision, not withdrawn (defence in depth, as in the reader view), from an active account (account row share-locked), status `open`, at the transaction time. A report therefore always names a revision that was published and readable when it committed.
- **Text rules.** Report text and resolution notes: CR LF and lone CR become LF, surrounding whitespace is trimmed, then 1 to 2000 characters of valid UTF-8 with no control character except LF (tabs are refused) and no bidirectional formatting or U+2028/U+2029 characters: the display-name rule (`invitations.NormalizeDisplayName`) with line feeds allowed, because the text is shown to reviewers and administrators and must not reorder surrounding text. Check constraints enforce the same characters, length and non-blank rule. The textarea carries no `maxlength`, because browsers count UTF-16 code units (an astral character counts twice) while the server counts characters; the hint states the limit and the server's `422` enforces it. The report form accepts bodies up to 32 KiB (2000 four-byte characters percent-encoded), other reader forms keep 8 KiB. A larger report body (text pasted far beyond the limit) is never accepted: its CSRF token cannot be checked, so nothing is stored and no throttle attempt is recorded; instead of the generic `403` page the signed-in reader gets the lesson page again with `413` and a message that the text was too long and could not be kept (the body was cut off). This read-only page needs no CSRF check; cross-origin posts are still refused before it.
- **Throttling.** `auth.Service.ThrottleErrorReport` reuses the login throttle table with two key scopes (`error-report-account`, the user ID; `error-report-address`, the client address from `auth.ClientAddr`): more than 10 submissions per account or 60 per address in 15 minutes return `429`. Every authenticated, CSRF-valid submission counts, invalid ones included, before validation; successful reports do not clear the counter. Requests refused for missing session or CSRF never reach the throttle. Throttled attempts are recorded too (as for login), so one account or client that keeps submitting while throttled keeps consuming the shared per-address budget: behind a shared NAT address, one student can lock out the others' reports for up to the window. **Pilot note (LRN-011):** a class behind one NAT address shares 60 reports per 15 minutes.
- **Status and resolution.** `error_reports.status` is `open`, `resolved` or `dismissed`. `error_report_resolutions` (report unique, actor, action `resolve` or `dismiss`, required note, transaction time, `xact_id`) is append-only. The resolution insert guard locks the report `FOR UPDATE`, requires it open and the actor an active administrator or active reviewer of the lesson's subject (rows share-locked); a deferred check requires the report's status to match by commit. The report guard allows only `status` to change, once, from `open`, with a resolution of the same transaction recording the matching action; every other column is immutable and rows are never deleted or truncated. The store locks the report row first, so of concurrent resolve and dismiss requests exactly one applies and the others get `409 not_open`.
- **Lock order and snapshots.** Filing: lesson row (share), then the reporter's account row (share); nothing else is locked, so the lesson-then-revision order is unaffected and reports never write to lessons or revisions. Resolution: the report row, then grant and account rows (share); the lesson's subject is read without a lock because it never changes. Every change that makes a revision unreadable (pointer change, withdrawal through `withdrawal_count`, archival) updates the lesson row, so a REPEATABLE READ or SERIALIZABLE writer whose snapshot predates it fails with `40001` (also through the foreign key's row lock); a resolution after a concurrent resolution likewise. At READ COMMITTED a report waits for an in-flight pointer change and is checked against its result. Tests cover both.
- **Reporter identity is not exposed.** The API returns no reporter ID or name; reviewers see the text, the revision and the time. **Open question:** whether administrators should see who reported (follow-up questions, abuse handling) and whether reporters should be told the outcome (LRN-020 notifications) or see their own reports.
- **Open question: duplicates and history.** Reports are not merged or rate-limited per lesson, and stay attached to the revision they named after a republication (`currentlyPublished` turns false). Whether a new publication should close or flag open reports is not decided.
- **Guard conventions and verification.** As in 0004–0008: `zz_guard_*` names, SQLSTATE `LRN01`, pinned `search_path`, `TG_TABLE_SCHEMA`-qualified references with bound parameters, no `SECURITY DEFINER`. A non-owner role on fresh connections with temporary shadow tables (`lessons`, `users`, `error_reports`, `error_report_resolutions`, `reviewer_assignments`, `user_permissions`, `revision_withdrawals`) is refused, or (for `revision_withdrawals`) unaffected, by every new guard. Mutation checks were run by hand on the key guards and store checks (pointer, archived and reporter checks, the lesson share lock, transaction-time checks, content immutability, delete and reopen refusal, status without or with a mismatched resolution, unqualified lookups in every function, resolution of a closed report, missing or subject-blind permission check, missing deferred check, mutable resolutions, missing unique resolution, unchecked characters, unscoped listing, unauthorized read and resolution, no report row lock, uncompared revision); each made at least one test fail. The `xact_id` condition in the report status guard is defence in depth: a resolution must be applied by its own transaction anyway, so no test can distinguish its removal. The threat model is unchanged: these guards bind a role that neither owns the tables nor is a superuser.
- **Not included.** Administration pages and audit log views (LRN-019), notifications (LRN-020), a reporter's list of their own reports, public or anonymous reports, automatic withdrawal or any change to lesson content.

## Deployment and recovery (LRN-010)

Implementer choices on 2026-11-24 within the execution contract on issue 10. Runbook: [DEPLOYMENT.md](DEPLOYMENT.md). Nothing is deployed; the shared-server rehearsal remains an open human acceptance item.

- **Image.** Multi-stage `Dockerfile`: pinned Node and Go images build the assets and `./cmd/server` only (no renderer experiment); runtime `gcr.io/distroless/static-debian12:nonroot` (uid 65532), base images pinned by version and digest. The Studio bundle is built in at `/opt/learnoo/studio`; since issue #65 it is served at `/studio` ([Studio integration](#studio-integration-issue-65)).
- **Listening in a container.** The loopback-only rule stays the default. `LEARNOO_ALLOW_NON_LOOPBACK=1` lets `serve` listen on the container interface, with a warning in the log. The image keeps the loopback default; the Compose file sets the address and the opt-in; Compose publishes the port only to `LEARNOO_HTTP_PUBLISH` (default `127.0.0.1:8090`) for the reverse proxy. Behind the proxy, client addresses need `LEARNOO_TRUSTED_PROXIES` (see [Trusted proxies and public base URL](#trusted-proxies-and-public-base-url-issue-46)); without it every client shares the proxy's address in the per-address throttles.
- **Roles.** `deploy/db/roles.sql` (superuser, idempotent) creates `learnoo_owner` (owns the database, schema objects and `SECURITY DEFINER` functions; runs migrations) and `learnoo_app` (runtime; `NOINHERIT`, member of no role), revokes `CONNECT`/`TEMP` on the database and on the `postgres` maintenance database from PUBLIC, all rights on `public` except `USAGE`, and every role membership of the runtime role. `deploy/db/grants.sql` (owner, idempotent, re-run after every migration by the Compose `grants` step) grants `SELECT, INSERT, UPDATE, DELETE` on all tables, `SELECT` only on views and `schema_migrations`, `USAGE` on sequences, revokes `EXECUTE` on `SECURITY DEFINER` functions from PUBLIC and the runtime role, and then fails if the runtime role has any role attribute, `TEMP`, `CREATE` on any schema, ownership of any object, any role membership, `TRUNCATE`/`TRIGGER`/`REFERENCES`, or `EXECUTE` on a `SECURITY DEFINER` function. Table-level DML is granted uniformly as the contract specifies; the append-only and immutability rules stay with the guards, which now bind the runtime role. Default privileges are not used, so a forgotten `grants.sql` fails closed (permission denied), never open. The error report tables of LRN-015 (migration 0009) get the same grants; the role test files and resolves reports as the runtime role and checks that their guards refuse unaudited status changes, edits, deletions, repeated or unauthorized resolutions and reports of withdrawn revisions.
- **Runtime start-up.** `database.Check` (used by `serve`) no longer creates `schema_migrations`; even `CREATE TABLE IF NOT EXISTS` needs `CREATE` on the schema. A missing table now reads as "all migrations pending". `server migrate` still creates it.
- **Passwords.** `LEARNOO_DATABASE_PASSWORD_FILE` supplies the database password from a file (Compose secret) instead of the URL. `initdb.sh` sets role passwords inside psql from secret files. The bootstrap superuser uses peer authentication on the socket and SCRAM over TCP; the database has no published port and sits on an internal network.
- **Probes.** `/healthz` is liveness only (no dependency), `/readyz` checks the database and media-directory writability with `access(2)`, which writes nothing; failures are logged and answered with a generic 503. `server probe` performs the container health check because the image has no shell or HTTP client. The reverse proxy must not expose either probe publicly.
- **Backups.** `deploy/backup.sh`: `pg_dump --format=custom` as the owner, then the media files listed, hashed and archived (`media.tar`, `media-files.sha256`), `info.txt` and `MANIFEST.sha256`; database first so every referenced (immutable) file is included. Media paths outside `[A-Za-z0-9._-]` segments are skipped and counted (never referenced by rows). `deploy/restore.sh` refuses non-empty targets, checks the manifest, validates every `media.tar` entry (regular files listed in `media-files.sha256` or directories, plain relative names; links and devices refused), extracts into a staging directory and checks every file, all before restoring the database in one transaction with `--no-owner` as the owner role (privileges as dumped); it then moves the media into place and re-runs `grants.sql`. The ops services run with read-only roots and no capabilities (restore: `CHOWN`, `FOWNER`, `DAC_OVERRIDE` only; backup as uid 65532). `server verify-restore` checks migrations, every media asset's file, size and SHA-256, publication pointers against status, withdrawals and the latest audit row, and reports row counts and unexpected or temporary files (never deletes; `-strict` fails on them). The rehearsal and negative cases run as Go tests on real PostgreSQL with the client tools (`psql`, `pg_dump`, `pg_restore`), which CI's runner provides.
- **Restored sessions.** A restore brings back the sessions that were valid at backup time. Whether a real recovery should also revoke all sessions (`DELETE FROM sessions`) is an operator decision; it is not automated.
- **Logging.** Unchanged: `log/slog` text records on stderr, start-up and errors only, no access log (use the proxy's). JSON logs or request logging were not added.
- **Values left to the infrastructure maintainer** (variables with EXAMPLE defaults in `deploy/production.env.example`, or open in DEPLOYMENT.md): app and PostgreSQL CPU, memory and PID limits and PostgreSQL shared memory; container log size and rotation count; backup frequency and schedule, retention period, on-host backup location, off-site location and its encryption; recovery point objective (RPO) and recovery time objective (RTO); alert destinations and thresholds; restore-rehearsal frequency; the published host address/port for the reverse proxy; reverse-proxy, TLS and Cloudflare configuration on the shared server (cache bypass for every authenticated path); production passwords and their rotation; the trusted proxy addresses, the client-address header and the use of Cloudflare (issue 46). None of these is settled by this work.

## Trusted proxies and public base URL (issue 46)

Implementer choices on 2026-11-24 (`internal/clientip`, `cmd/server`; runbook in [DEPLOYMENT.md](DEPLOYMENT.md#client-addresses-behind-the-proxy)).

- **One resolution point.** `clientip.Middleware` (installed by `serve` around the whole handler) resolves the client address once per request and stores it in the context; `auth.ClientAddr`, used by the login, invitation and error-report throttles, reads it and falls back to the TCP peer when the middleware is absent (tests, tools). No handler reads forwarding headers. Headers are not rewritten and `RemoteAddr` is not changed.
- **Trust.** `LEARNOO_TRUSTED_PROXIES` is empty by default: forwarding headers are then ignored entirely. Headers are read only when the immediate peer is in a trusted range; ranges broader than /8 (IPv4) or /16 (IPv6) are refused, including mapped forms. Which address to trust is infrastructure configuration, not code; the runbook recommends only the reverse proxy's own address and warns that a published port makes every host process arrive from the trusted Docker gateway.
- **Header.** `X-Forwarded-For` by default, walked from the right to the first untrusted address (client-prepended entries are ignored; when no untrusted address is found, the nearest hop is used: the right-most entry if it is a valid trusted address, otherwise the peer, never an entry further left; at most 32 hops). `CF-Connecting-IP` is an alternative for a proxy reachable only from Cloudflare; exactly one valid header is required, otherwise the peer is used. The standard `Forwarded` header and `X-Real-IP` are not supported.
- **Open infrastructure decision: Cloudflare.** Trusting Cloudflare's published ranges in `X-Forwarded-For` mode is not safe: Cloudflare Workers of any customer egress from inside those ranges (for example `2a06:98c0:3600::103`) and can forge the entries to their left, so every Cloudflare-originated client would be trusted. With Cloudflare in front, the runbook points to `CF-Connecting-IP` with an origin reachable only from Cloudflare, trusting only the proxy. Whether and how Cloudflare is used, the origin lockdown and the final header choice stay with the infrastructure maintainer.
- **Shared networks.** Students behind one NAT (a school) still share an address; the per-address limits were chosen with that in mind (see the reader and error report sections).
- **Public base URL.** `LEARNOO_PUBLIC_BASE_URL` (an `https` site root: no credentials, path, query or fragment) is used by `invite-student` for links. Without it, the command keeps printing `http://<loopback LEARNOO_ADDR>` links for local development and refuses a non-loopback address. It is printed, so it must contain no secret. The server itself does not use it (it builds no absolute URLs).
- **Not included:** access logging (excluded by the issue) and choosing the production proxy or Cloudflare settings (infrastructure maintainer).

## Studio integration (issue #65)

Implementer choices on 2026-11-25 (`internal/catalogue`, `internal/studioapi/studio.go`, `internal/studioweb`, `internal/rendering/lesson.html`, `migrations/0010_catalogue_audit.sql`, renumbered at merge; routes in [API.md](API.md#studio-integration-issue-65)). Codes are validated in Go against the existing CHECK pattern before the database is touched (strictly: no lower-casing, unlike `grant -subject`), repeats are a reported no-op without an audit row, and nothing renames or deletes entries. `grants.sql` covers the new table through its `ALL TABLES` grant; the runtime-role test still passes.

It requires `author` in the middleware and inside its `REPEATABLE READ` transaction, so a revoked author is refused. Ordered by the latest revision's `updated_at` (or the lesson's creation when the only draft was discarded), at most 500, without paging: a pilot author has far fewer.

The loopback renderer experiment is untouched and unused.

Every response, assets included, needs a session and Studio access (`author`, `publisher`, `administrator` or any reviewer assignment): page requests without a session redirect to `/login?next=/studio…` (the sign-in page now accepts `/studio` paths), students get the reader's 403 page, and asset requests are `404` for both so file names are not revealed. Paths without a dot in their last segment are client routes and get `index.html`.

## Studio authoring frontend (issue #66, first slice)

Implementer choices on 2026-11-25 (`web/studio/src`; usage in [DEVELOPMENT.md](DEVELOPMENT.md#using-the-studio-authoring)). This slice covers authoring; the reviewer, publisher and administrator views are the [second slice](#studio-review-publication-and-administration-issue-66-second-slice). Items marked **to confirm** are left to the maintainer.

- **No new dependencies.** Routing is a small History API router (`router.ts`), dialogs are the native `<dialog>` (focus trap, Escape, inert background), the API client is `fetch`. Routes: `/studio/` (my lessons), `/studio/lessons/new`, `/studio/lessons/{lessonId}/edit`; none has a dot in its last segment. The numeric lesson ID is used because the owned-lesson listing and the draft endpoints are keyed by it; `publicId` stays for reader URLs. The shell shows navigation only for spaces the account can use (today: "Mes leçons" for authors, detected by `GET /api/lessons/mine` answering 403); the server still enforces every rule.
- **Server is the only persistence.** The prototype's `localStorage` save/reopen (`schema/storage.ts`) is removed. Saves are explicit (button, `Ctrl/Cmd+S`), version-checked, and never automatic: an automatic save would race the conflict rule and create versions the author did not choose. A new lesson is created by its first save, because a lesson must start with a valid schema v1 draft (non-empty), and inventing placeholder content would put unreviewed text on the server. That save only replaces the address (`history.replaceState`): the editor stays mounted, so text typed while the request is in flight is kept and stays marked unsaved (the saved baseline is what was sent). The same holds for every save, so fields are not disabled during saves.
- **Unsaved-edit recovery buffer.** While edits are not saved, a copy (TipTap JSON plus title, objective, prerequisites, chapter and media IDs, so invalid intermediate states survive) is written to `localStorage` about 0.7 s after each change and on `pagehide`/`beforeunload`. Keys are `learnoo-studio-recovery:v1:u{user}:r{revision}:v{base version}:{editor instance}` (`…:new:…` for a lesson not yet created, `…:lesson-{id}:new:…` for a lesson without a revision); each copy also records its lesson and revision number, so copies written on a revision that has since been submitted or discarded are still offered on that lesson (copy/delete on the read-only view, restore on the next draft). The instance (one per tab and page load) prevents two tabs, or a reopened tab, from overwriting a copy the author has not seen. A copy is never loaded or sent without the author's action: copies for the revision from other instances are listed as "Copies de secours locales (non enregistrées)" with Restaurer / Copier / Supprimer. A copy is removed when its content is saved (the editor's own copy and a restored one), when this tab deletes the draft (other tabs' copies are kept and offered on the lesson's next draft), when the author deletes it, or silently when it equals the server's content. Shared devices (maintainer decision, 2026-11-25): signing out deletes every copy of that account from the browser, after a warning whenever the page has unsaved edits or the account has copies, and nothing is written afterwards; copies older than 14 days, of any account, and unreadable entries are deleted when the Studio starts. Another open tab of the same account that still holds unsaved edits rewrites its copy after a sign-out purge, by design: those edits are still on its screen, and the copy disappears with the next save or sign-out there.
- **Submitted elsewhere.** A `409 not_draft` (the draft was submitted from another tab) opens a panel like the conflict one: the edits stay in the editor and in a lesson-level copy, which can be copied at once, is listed on the read-only revision and can be restored into the corrected version.
- **Conflicts.** A `409 version_conflict` on save or submit writes the local edits to the buffer as a "conflict" copy and opens a panel (focused, `aria-labelledby`) that keeps the editor untouched. "Charger la version du serveur" loads the server's draft; the local copy is then offered for restore (the author merges by hand and saves against the new version) or copy. "Copier mon contenu local" uses the clipboard, with a selectable text fallback. There is no automatic merge. `409 retry` is repeated once automatically (nothing was written). A rejected CSRF token is refreshed from the session once and the request repeated.
- **Session expiry and account changes.** A 401 at start-up redirects to `/login?next=<current /studio path>`. After start-up it shows a banner instead of redirecting, so nothing on the page is lost: the author signs in in a new tab and resumes (the new CSRF token is read before the next write). The API client remembers the account the page started with and checks it on every session read, including the CSRF refresh before a retried write: if the browser's session now belongs to another account (someone signed in as another user in another tab), it throws `account_changed`, keeps none of that session's token, sends nothing (reads included) and the page shows "Un autre compte est connecté dans ce navigateur" while keeping the edits. A stale tab can therefore never create, save, upload or submit as another account. Reads are guarded too: before a read, the account is re-checked when the last check is older than 3 seconds or was invalidated by an in-app navigation or by the tab becoming visible or focused again (which also re-checks at once), so a page never lists another account's lessons under its own header. Saves, uploads, submission and discard are also refused locally while the banner is shown; "Reprendre ici" succeeds only once a session of the original account is back.
- **Images.** Schema v1 has no node for uploaded media (images are limited to the renderer's fixture allowlist), so uploads are attached as `mediaIds` and listed with thumbnails (`/api/media/{id}`, allowed by `img-src 'self'`), not inserted into the text. Placing uploaded images in the document needs a schema change shared with the Go validator and reader, outside this slice (issue #77). Attached images are visible to the author and reviewers but not yet shown to students; the upload panel says so. *Superseded by [embedded images (issue #77)](#embedded-uploaded-images-issue-77).* Client checks (type, 5 MiB) only avoid pointless uploads; server codes are explained in French (`trailing_data`, `type_mismatch`, `invalid_dimensions`, `busy`…).
- **Preview without iframe.** The server's HTML (`POST /api/preview`, escaped and allowlisted by the reader's templates) is placed in a `.lesson-preview` element. The reader's `site.css` and `reader.css` are nested under `.lesson-preview` at build time by a Vite plugin (`web/studio/tools/scope-css.ts`: `body`/`main` rules apply to the container, plain `:root` rules dropped, `@media` nested; any other at-rule such as `@font-face` or `@keyframes`, and `:root`/`html` elsewhere, fail the build rather than leak), so the preview cannot drift from the reader's styles and cannot restyle the Studio. KaTeX is loaded on demand from `/static/vendor/katex/` (same origin, allowed by the existing CSP) and run with the reader's options (`preview.ts` mirrors `math.js`). The YouTube button is disabled in the preview because the Studio's CSP allows no frames; no CSP change was needed. The renderer experiment's `/preview` is no longer called, and the prototype's Vite-preview browser test is replaced by the Go-served tests in `tests/browser-reader/studio.spec.mjs`.
- **Workflow.** Submit asks for confirmation and saves pending edits first. Revisions that left draft are shown read-only through the canonical preview, with their state, the reviewer's comment (`GET /api/revisions/{feedbackRevisionId}`) when `hasFeedback`, and "Créer la version corrigée" / "Créer une nouvelle version" when the server would accept a successor (changes requested, or the latest revision is the published one); the successor starts from the previous revision's content, prerequisites, chapter and media. `active_candidate_exists` is explained (approved revision awaiting publication or withdrawal). Discard asks for confirmation with the safe choice focused.
- **Accessibility and motion.** The editor is named "Éditeur du contenu de la leçon", distinct from the preview's "Contenu de la leçon" article. French interface, `lang`/`dir` from the lesson language on the editor, title, objective and prerequisites (Arabic lessons edit right to left), polite live region for the save state, alerts for failures, focus moved to the page heading on navigation and to the conflict panel when it opens, skip link, 44 px targets, no animation (nothing to reduce for `prefers-reduced-motion`).

- **Lesson publication read.** Withdrawal, unpublication and restoration need the revision IDs and the current pointer, so `GET /api/lessons/{lesson}/publication` (publisher or administrator, numeric ID or public ID) returns submitted revisions with their approval, publication and withdrawal state and the pointer audit. The audit log is the administrator's (CAHIER_DES_CHARGES §2.2), so after review the conservative reduction applies: callers without `administrator` get only what restoration needs (current pointer; approved revisions' number, title, approval time and ever-published, withdrawn and candidate flags) with no names, reasons, history, or revisions in review or sent back. The publication page says so ("Vue éditeur"); `GET /api/admin/lessons` (administrator) lists lessons with an approved revision so an administrator without other roles can find one. Pages for the pointer audit and withdrawals beyond this minimum stay LRN-019.
- **Preview for every Studio account.** `POST /api/preview` was author-only; reviewer-only, publisher-only and administrator-only accounts could not render what they decide on. It is now open to the `/studio` access rule (author, publisher, administrator or any reviewer). It renders the posted document and stores nothing, so no data is exposed; reviewers render the revision returned by the review endpoint, publishers the one from the publish read. No separate stored-revision renderer was added.
- **Author names.** The review queue returns `authorName` (display name) so reviewers see who wrote a revision; the publication reads return author, approver and actor names. These are staff-only responses; readers already see author and approving-reviewer credits. Reviewer identity on change requests (an open question) is not shown to authors by this slice. **To confirm** whether reviewing should be blind.
- **Confirmations and required text.** Every decision (approve, request changes, publish, withdraw, unpublish, restore, resolve or dismiss a report) opens a native `<dialog>` restating the effect, the text that will be stored and, for pointer changes, the expected published revision ("Version publiée attendue : …"); focus starts on the safe choice. Required comments, reasons and notes are checked before the dialog opens (inline error, focus on the field), and the server's `comment_required`/`reason_required`/`note_required` are explained the same way if they still occur.
- **Self-review.** A reviewer opening their own in-review revision (it is not in their queue, but readable by URL) sees why they cannot decide and no decision buttons; `self_review` from the server is explained if it occurs.
- **Focus and loading.** After a withdrawal, unpublication or restoration the focus moves to the outcome banner (the pressed button may be gone). Page loads ignore responses to older requests, so a slow earlier load (for example the previous report filter) never replaces a newer one. "Corrigé" and "Écarté" reports have distinct styles besides their words.
- **Stale pointer.** Pointer-changing actions send the published revision loaded with the page. On `stale_pointer` the page says nothing changed and offers "Recharger l’état actuel"; it does not reload by itself, so the administrator sees that the state moved before acting again.
- **Restoration and withdrawal offers.** Restore is offered only for approved, previously published, non-withdrawn revisions that are not current (the server's conservative rule); withdrawal for approved, non-withdrawn revisions, with an explicit warning when the revision is the published one (the lesson is unpublished too).
- **Recovery copies at sign-out.** The coordinator decided that signing out deletes the user's recovery copies (privacy on shared computers); the first slice implements it (`purgeRecovery` with the user, after the unsaved-edits warning). This slice keeps that single implementation.
- **Account changes.** Editorial calls go through the same client as authoring, so after another account signs in on the browser every request is refused locally (`account_changed`) until the original account is back, and the page explains it.
- **Not included.** Publisher and administrator access to uploaded media of approved revisions (the publish page lists their number; schema v1 cannot place them in the lesson anyway; *publishers gained a media route with [issue #77](#embedded-uploaded-images-issue-77)*), re-probing spaces after a permission change, reviewer assignment lists per subject (the queue groups only subjects with revisions), dashboards and notifications (M2), LRN-019 administration pages beyond these actions.

## Embedded uploaded images (issue #77)

Implementer choices on 2026-11-25 (`internal/rendering`, `web/studio/src/schema`, `internal/lessons`, `internal/studioapi`, `internal/reader`, `internal/media/serve.go`; routes in [API.md](API.md)). Also closes issue #57. Items marked **to confirm** are left to the maintainer.

- **Compatible schema v1 extension, not v2.** An `image` node's `src` is now either an allowlisted fixture asset (unchanged) or `media:<id>`: `media:` and a positive decimal media ID without sign or leading zeros, at most 15 digits. Media IDs are int64 database identities, but 15 digits keeps every valid ID below 2^53, so the Studio reads it exactly as a JavaScript number (no `BigInt` or string IDs needed); 10^15 uploads are unreachable, and if the bound ever mattered it would be a deliberate contract change in both validators. A new optional `caption` string (at most 1,000 bytes, like `alt`; only on images) is added after `alt` in field order; an empty `caption` is the same as an absent one, on any node, exactly like other empty optional strings (`omitempty`), and is dropped on canonicalization. `alt` stays required and bounded (1,000 bytes) and must now contain a character that is not white space, for fixture and uploaded images alike: both validators refuse an `alt` made only of the union of Go's `unicode.IsSpace` and JavaScript's `trim` set, listed by code point in both (`rendering.blankText`, `lesson.ts` `BLANK`) so they agree (U+0085 and U+FEFF included; a zero-width space is not white space). This tightens v1 for one input that was accepted before (a whitespace-only `alt`); the fixtures, golden exports and contract cases have real alt text, and no stored pilot document is expected to have a blank one; if one existed, its next submission or restoration would be refused with `invalid_content` rather than silently changed. The Studio trims alt text and caption on export. Every other document valid before stays valid and canonicalizes to the same bytes (no new field is emitted when absent), so no migration and no version bump are needed: `schemaVersion` stays `1`, stored revisions and the fixtures are untouched. Go (`rendering.Validate`) and the Studio (`lesson.ts`) give the same verdict on 41 new contract cases (valid references, nesting, mixing with the fixture image, missing, empty, whitespace-only (ASCII, no-break, ideographic, U+0085, U+FEFF) or over-long alt, captions empty, out of place or `null`, IDs `0`, `05`, signed, 16 digits, above 2^53, empty, with spaces, upper-case scheme, paths, non-ASCII digits, API or reader URLs, `data:` URLs).
- **Immutable reference by media ID.** The content names the asset (`media_assets.id`, immutable and never deleted), never a URL: URLs depend on who reads the page. The revision's `mediaIds` (`revision_media`) stay the attachment list. On every create and save, each embedded ID must be in `mediaIds` (`422 unattached_media`), and `mediaIds` must be readable by the author (`422 unknown_media`, as before, the same answer as for a missing asset), so the content can only show images its author may read. Submission (and restoration, through `CheckStoredContentTx`) rechecks the stored snapshot against `revision_media` inside the transaction; once submitted, the existing guards freeze both content and `revision_media`. The Studio adds every embedded ID to `mediaIds` when saving. Removing an image from the text does **not** detach it: it stays attached until the author removes it from the revision ("Retirer de la révision" is disabled while the image is in the text). Attached but not embedded images are reviewed (the review page lists them) but never shown to students (below). **To confirm** whether unplaced attachments should be dropped automatically at submission.
- **Rendering with a viewer-specific URL.** `rendering.RenderLesson(doc, media)` takes a `MediaURL` (a function from ID to URL; `MediaPrefix(prefix)` for the common case) and renders a copy of the document whose `media:` sources are replaced, so stored snapshots are never modified. Studio preview: `/api/media/{id}` (author), `/api/review/media/{id}` (reviewer) or `/api/publish/media/{id}` (publisher), chosen by the preview request's `mediaRoute`. Reader: `/learn/lessons/{publicId}/media/{id}`. The preview and the reader page therefore stay byte-identical except for those `src` attributes (tested by swapping the prefix); documents without uploaded images are byte-identical as before. The local renderer experiment and any caller passing `nil` refuse documents with uploaded images (`ErrNoMediaURL`) instead of emitting a broken or unchecked URL; html/template would neutralize an unresolved `media:` URL anyway. Uploaded images render as `<figure class="lesson-media"><img src alt loading="lazy">…</figure>` without fixed `width`/`height` (the document does not carry dimensions; `site.css` keeps them at natural size up to the column width) — a possible layout shift while loading, accepted for the pilot.
- **Captions and alt text (issue #57).** A `<figcaption>` is rendered only from `caption`, for fixture and uploaded images alike, never from `alt`, so screen readers announce each image once. This deliberately changes the rendered markup of the existing fixture image (`complex-numbers`): its `<figcaption>` repeating the alt text is gone. The fixtures' JSON and every stored document are unchanged.
- **Reader media route.** `GET /learn/lessons/{publicId}/media/{mediaId}` serves an image only when the lesson's current published revision as defined by `reader_published_lessons` (approved, not withdrawn, lesson not archived) both lists it in `revision_media` and embeds it in its content (a `jsonb_path_exists` on `"type": "image"` nodes with `src = "media:<id>"`), to any signed-in account, as lesson pages are. Scoping by lesson (rather than a global `/learn/media/{id}`) means an image is readable exactly while a lesson that shows it is readable, with no cross-lesson lookups, and the route answers the same JSON `404` for everything else, anonymous requests included (no sign-in redirect for an image, like protected `/static` media). Unpublication, withdrawal and archival stop serving at once; restoration serves the restored revision's images. Headers are shared with the Studio media routes (`media.Store.Serve`): `private, no-store`, `nosniff`, `inline`, a sandboxing CSP, content type from the validated storage key. The reader's and Studio's `img-src 'self'` suffice; no CSP changed. No new SQL objects (no migration): the query reads the existing view and tables, and the runtime-role flow now publishes an embedded image and fetches it through this route.
- **Publisher media route.** Publishers read approved revisions through `GET /api/publish/revisions/{id}` but had no access to their images (the reviewer route covers revisions in review only). `GET /api/publish/media/{mediaId}` serves an asset referenced by a revision awaiting publication (the publisher queue rule, `review.AwaitingPublication`) to holders of `publisher`; anything else is `404`. Administrators read no revision content (their views show publication state and history), so they get no media route; they see published images in the reader like any account.
- **Studio.** "Placer dans le texte" on an attached image opens a dialog (native `<dialog>`, focus on the alt field) asking for the required alt text and an optional caption; the image is inserted at the editor's cursor (after a selected node instead of replacing it). The editor shows it from `/api/media/{id}`, with its alt text visible in the figure for the author; the inspector edits alt and caption. Copy and paste inside the Studio keeps the reference (`data-src`); pasted reader or API image URLs are dropped, never turned back into references. The review and publication pages pass their own `mediaRoute` to the preview.
- **Students and "other users".** Any signed-in account can read a published lesson, so any can fetch its embedded images; "no other user" means no access outside that rule: anonymous requests, other lessons' paths, unpublished, withdrawn or archived revisions, drafts, attached-only images, and the author, reviewer and publisher routes for accounts without those roles (tested in Go and Playwright).
- **Not included.** Image dimensions in the document, responsive variants, and per-image access outside lessons; video uploads and phone-photo formats (#42) stay out of scope.

## Submission audit

Implementer choices on 2026-11-26 (`migrations/0011_submission_audit.sql`, `internal/lessons` `Submit`). CONTENT_AND_EDITORIAL.md requires actor, revision, action and timestamp to be recorded for submission as for decisions, publication, unpublication, restoration and withdrawal, which were already audited (0006, 0007). Submission was recorded only by `lesson_revisions.submitted_at` and `author_id`.

- **Table.** `submission_audit` (lesson, revision unique, `actor_id`, `submitted_at`, `xact_id`, `backfilled`). The action is implicit (a revision is submitted once; the table name is the action), so there is no `action` column. Append-only: update, delete and truncate are refused by `zz_guard_*` triggers using 0006's `review_audit_append_only` (SQLSTATE `LRN01`). The composite foreign key keeps the revision inside the lesson, and also stops deletion of a draft that already has its row in the same transaction.
- **Submission and audit stay consistent in the database** (the pattern of decisions in 0006 and of the pointer audit in 0006/0007). A revision leaves `draft` (for `in_review`, the only transition 0004 allows) only together with a `submission_audit` row for it written by the same top-level transaction (`xact_id = pg_current_xact_id()`), not backfilled, naming its lesson and author, and its `submitted_at` must be the transaction time, which the audit row records too; a deferred constraint trigger requires every audit row to have moved its revision out of `draft`, with the same `submitted_at`, by commit. The order is therefore fixed: audit row first, then the status update (the update guard needs the row, and the insert guard needs a draft). A rollback, including to a savepoint taken between the two, leaves both or neither: an audit row whose status change was rolled back fails at commit.
- **Insert guard.** Refuses `backfilled = true`; requires the transaction time and the writer's own `xact_id` (no backdated, future or forged rows); a revision of `lesson_id`; the lesson not archived (share-locked first, so it cannot be archived meanwhile); the revision a draft, locked `FOR UPDATE` after the lesson (lock order lesson, then revision, as `Submit`, the decision guard and the pointer triggers); `actor_id` equal to the revision's `author_id`; and the actor an active account holding `author` (grant and account rows share-locked, as `permissions.RequireTx`). These mirror the store's checks (`RequireTx(author)`, own draft, not archived), which still run first and keep their error mapping; the database adds them for every writer the guards bind. The store's version check and the content recheck stay store-only (the database does not know the expected version and cannot run the schema v1 validator). Since 0004 binds `author_id` to the lesson's owner, the submitter is always the owner too.
- **One submission per revision.** `revision_id` is unique and a revision never returns to draft. Of concurrent submissions of one draft, the store serializes them on the revision lock and the loser gets `not_draft` or `version_conflict`. A concurrent direct-SQL submitter waits on the revision lock the insert guard takes `FOR UPDATE`, then re-reads the revision and is refused by the guard (`LRN01`, "is not a draft"); the unique `revision_id` is the backstop (it would answer `23505`). Tested with concurrent `Submit` calls and with two direct-SQL submitters (one success, one row, the loser refused by the guard; removing the `FOR UPDATE` makes that test fail). In the update guard, the `xact_id` match is a backup to the commit-time check, which already makes a committed audit row of another transaction impossible for a draft.
- **Revision time.** `Submit` now sets `submitted_at` and `updated_at` to the transaction time (`now()`) instead of the store's Go clock, so the revision and its audit row carry the same instant; the guard enforces it for every writer. For consistency every timestamp `lessons.Store` writes is now the database transaction time (lesson `created_at`, revision `created_at`/`updated_at` on creation and save), like the audit tables and `review.Store`; the unused clock parameter of `lessons.NewStore` was removed (no caller injected a clock). The API fields keep their meaning.
- **Stale snapshots.** A writer at `REPEATABLE READ` or `SERIALIZABLE` whose snapshot predates a change that would deny the submission cannot submit with it: a concurrent submission updates the revision row the guard locks `FOR UPDATE`, archival updates the lesson row it share-locks, revocation deletes and disablement updates the grant and account rows it share-locks (all `40001`); a grant committed after the snapshot is invisible, which denies. The commit-time check reads only rows the transaction locked or wrote. Tested for revocation, disablement and archival at both levels.
- **No `SECURITY DEFINER`.** Nothing here writes another table from a trigger, so every new function is a plain guard with the usual hardening: pinned `search_path = pg_catalog, pg_temp`, other tables reached through `TG_TABLE_SCHEMA` with bound parameters. A non-owner role holding only DML grants and `TEMP`, on fresh connections, is refused with temporary shadow tables `submission_audit`, `lesson_revisions`, `lessons`, `user_permissions` and `users`, and can still submit legitimately without them. Mutation checks were run by hand (unpinned and unqualified lookups, no deferred check, no archived check, no actor check, no revision-time check); each made at least one test fail. The runtime-role deployment test checks that its HTTP submissions were audited and that it cannot truncate, edit or delete the audit, submit without a row, or audit a submission for another user, backdated, or without a status change.
- **Backfill of upgraded databases.** Revisions submitted before 0011 (`in_review`, `changes_requested`, `approved`) have no row, yet the audit should cover every submitted revision (and `verify-restore` now checks that). The migration inserts one row per such revision, before creating the guards, with `actor_id = author_id`, `submitted_at` = the revision's recorded `submitted_at`, `xact_id` = the migration's transaction and `backfilled = true`, so rows reconstructed from the revision are distinguishable from rows observed at submission. Why `author_id` is a sound actor: since LRN-006 only the draft's author could submit through the store, and a revision's `author_id` is its lesson's owner for every writer (0004); only direct SQL bypassing the store could have submitted otherwise, and the revision records nothing more about it. A backfilled row therefore asserts no more than the revision itself already did. The insert guard refuses `backfilled = true`, so new rows cannot claim it; only the migration (or a restore, which loads data before creating triggers) holds backfilled rows. Drafts get no row. Alternatives rejected: leaving old revisions unaudited (the audit and the restore check would then have to special-case them forever) and marking the actor unknown (`actor_id` NULL, weakening the column for every future row to cover a one-off). Tested by migrating a schema to 0010, creating published, changes-requested, in-review and draft revisions with 0010's rules, then applying 0011: one backfilled row per submitted revision with its author, its `submitted_at` and the migration's transaction (the `schema_migrations` row's), none for the draft, and the guards active afterwards. A fresh database starts with no rows.
- **Exposure.** Additive only. The administrator view of `GET /api/lessons/{lesson}/publication` gains `revisions[].submission` (`submittedBy`, `submittedAt`, `backfilled`; `null` for publishers). Submissions are not merged into that view's `history`, which stays the pointer audit, so its `action` values are unchanged. The revision object gets no submitter field: the database guarantees the submitter is `authorId`, and `submittedAt` already equals the audit time. `verify-restore` (`internal/backupcheck`) reports a submitted revision without its row, a row disagreeing with its revision, and a draft with a row.
- **Tests that simulated submission.** LRN-006 tests that moved a revision to `in_review` with a bare `UPDATE` now use `dbtest.Submit`/`dbtest.SubmitTx`, which write the audit row and the status change in one transaction as the database requires; their assertions are unchanged.
- **Threat model unchanged.** These guards bind a role that neither owns the tables nor is a superuser; an owner can still disable triggers, which `verify-restore` would then report as a missing row.

## Catalogue names and order (issue #86)

Implementer choices on 2026-11-26 for the technical part of LRN-014 (`migrations/0012_catalogue_names.sql`, `internal/catalogue`, `cmd/server`, `internal/studioapi/studio.go`, `internal/lessons/owned.go`, `internal/reader`, `web/studio/src/catalogue.tsx`; routes in [API.md](API.md#catalogue)). The pilot catalogue seed stays blocked on teacher input and contributor terms: no curriculum data is added, and fixtures use `TEST` names.

- **Identity versus display.** Codes, IDs, creation times and a chapter's subject stay immutable (the 0004/0010 identity guards are unchanged): reviewer grants, lessons, revisions and URLs name entries by ID or code. French and Arabic display names (`name_fr`, `name_ar`) and a display order (`sort_order`) are added to `subjects` and `chapters` as mutable display metadata.
- **Names nullable until set.** Names are `NULL` until an operator sets them, and every reader and Studio view falls back to the code, so existing installations upgrade without invented names and an entry can be named in one language first. New entries start without names and with order 0 (a guard refuses anything else on insert), so every name a reader sees went through an audited change. The command line cannot remove a name (the database allows it with its audit row); a correction replaces it.
- **Name rule.** Trimmed, 1 to 200 characters, without control (Cc), format (Cf) or line/paragraph separator (Zl, Zp) characters: the operator label rule of 0002/0003/0010, listed by code point in `catalogue_valid_name` (an immutable SQL function with a pinned `search_path`, used by the CHECK constraints on the entries and the audit) and applied in Go by `catalogue.NormalizeName` (`unicode.In(Cc, Cf, Zl, Zp)`, at least as strict). Arabic is accepted; the Arabic letter mark (U+061C, Cf) is not. Names are not unique: two entries may share a name, and the code stays the identifier. **To confirm** whether names should be unique per subject.
- **Order.** `sort_order` is an integer from 0 to 9999, default 0; lists sort by order, then code (the API, the operator listing, the reader's dashboard and chapter groups, the Studio pickers and the review queue). An explicit integer rather than a position list keeps each reorder a single audited row; gaps (10, 20, 30) leave room for insertions.
- **Same-transaction audit.** `catalogue_audit` gains `rename_subject`, `rename_chapter` (old and new values of both names), `reorder_subject` and `reorder_chapter` (old and new order). Three guards keep it exact for every non-owner role: (1) the audit guard requires a row's old values to be the entry's current values (and the CHECK requires a change); (2) `zz_guard_subjects_metadata`/`zz_guard_chapters_metadata` refuse a name (order) change unless the latest rename (reorder) row of the same transaction for that entry records exactly that change; (3) a deferred constraint trigger (`zz_guard_catalogue_audit_applied`) requires at commit that each such row was applied: the next row of the same kind, entry and transaction starts from its new values or, for the last, the entry still has them. So an unaudited update, an audit row for a change that was not made, an undone change and an audit row reused for a second change all fail. The operator path locks the entry (`FOR NO KEY UPDATE`), writes the audit row, then updates, in one transaction; repeats with the current values write nothing.
- **Concurrent catalogue writes and stale snapshots.** The audit guard itself locks the entry (`FOR NO KEY UPDATE`, held to the end of the transaction, the same lock and order as the operator path), so two transactions cannot both audit a change from the same values. A writer whose snapshot is stale waits for the other transaction: at READ COMMITTED the guard then reads the committed values and refuses a row built on the old ones (`LRN01`), at REPEATABLE READ and SERIALIZABLE the lock fails with a serialization error (`40001`); either way nothing is written, and the writer must reread and retry. Without the lock, a review found that a direct-SQL writer at READ COMMITTED could commit a duplicate rename row for a change it never made while another transaction made it. Operator commands run at READ COMMITTED and lock before reading, so concurrent commands simply apply one after the other, each audited from the values it actually changed. The update guard's old-value comparison stays as defence in depth: a test plants a stale row with the audit guard switched off (as the table owner) and the update is still refused. Concurrency tests use two connections for the duplicate row and for an A→C rename racing a committed A→B, at each isolation level; removing the lock, or the update guard's old-value comparison, makes them fail. All guards use `LRN01`, `zz_guard_*` names, a pinned `search_path`, `TG_TABLE_SCHEMA`-qualified lookups with bound parameters, and none is `SECURITY DEFINER`. A test runs them as a non-owner role on fresh connections with temporary shadow `catalogue_audit`, `subjects` and `chapters` tables; mutation checks (unpinned, unqualified lookups in each of the three functions; matching any audit row instead of the latest; dropping the deferred check) each made at least one test fail. The threat model is unchanged: these guards bind a role that neither owns the tables nor is a superuser. `grants.sql` needs no change (the new function is not `SECURITY DEFINER`); the runtime-role and backup/restore tests pass with names set.
- **Names are not reviewed content.** Lesson revisions store `chapter_id`; submitted snapshots contain no catalogue name, and names are joined at read time. Renaming a chapter therefore changes how every lesson placed in it is labelled, published ones included, without a new review. That is intended: it is an administrator catalogue action ([CAHIER_DES_CHARGES.md](CAHIER_DES_CHARGES.md): "Manage curriculum catalogue"), done today by operators, audited with old and new values, and limited to display. Moving a lesson to another chapter still needs a reviewed revision.
- **Display language.** The reader's interface is French: navigation (dashboard subjects, subject heading, chapter headings) prefers the French name; a lesson's breadcrumb and its context in bookmarks and search results prefer the lesson's language. The Studio uses the language of the lesson concerned (the language chosen on the new-lesson form, the edited lesson, a lesson in the list, a revision under review) and French on the review queue and report pages. Each falls back to the other language's name, then the code. Arabic names are marked `lang="ar" dir="rtl"` (`<bdi>` in running text, attributes on picker options).
- **API.** Additive: catalogue entries gain `nameFr`, `nameAr` (null when unset) and `sortOrder`; `GET /api/lessons/mine` gains `subjectNameFr`, `subjectNameAr`, `chapterNameFr` and `chapterNameAr`. The publisher and administrator lesson lists still show codes (they cannot read the catalogue; see "Catalogue scope" above).
- **Migration number.** 0012, after the submission audit (0011), which it does not depend on; the upgrade test applies every migration before 0012 (0001 to 0011) to a schema with existing subjects and chapters, then 0012.
- **Not included.** The pilot seed and any real name (LRN-014, teacher input), sections, a web page for catalogue administration (LRN-019) and public catalogue pages (LRN-024).

## Fingerprinted static assets (issue #88)

Implementer choices on 2026-11-26 (`internal/reader/assets.go`, `internal/studioweb`, `web/studio/src/preview.ts`; routes in [API.md](API.md#fingerprinted-assets-assetsversionpath), proxy rules in [DEPLOYMENT.md](DEPLOYMENT.md#caching-reverse-proxy-and-cloudflare)). Phase 1 asks for public asset caching; [LMS_PRODUCT_SPEC.md §10](LMS_PRODUCT_SPEC.md) allows caching only content without identity-dependent data and forbids shared caching of protected HTML, API, previews and media.

- **What is public.** The reader's generic `tokens.css`, `site.css`, `reader.css`, `math.js` and the vendored KaTeX (`katex.min.css`, `katex.min.js`, fonts): the same set that was already served without a session under `/static/`. They contain no user, lesson or permission data, are identical for everyone, and are open-source or project code. **Decision: they are served without a session** and may be stored by browsers and shared caches. Lesson media (the fixture image, uploaded images), the renderer experiment's files and KaTeX's `LICENSE` are not fingerprinted.
- **URLs.** `/assets/<version>/<name>`, where `<name>` is the file's former `/static/` name and `<version>` the first 16 hex digits of a SHA-256. A per-file digest for the reader files; for KaTeX one digest over the whole directory (sorted names, sizes and contents), so that the fonts `katex.min.css` references by relative URL (`fonts/…`) resolve under the same version without rewriting KaTeX's stylesheet. Changing any KaTeX file changes every KaTeX URL, which is acceptable for a pinned dependency. A dedicated `/assets/` prefix rather than `/static/<hash>/…`: a CDN can then select exactly the cacheable paths with a plain prefix rule (Cloudflare's "starts with"; regular-expression matching is not available on every plan) and cannot confuse them with the unversioned `/static/` files.
- **Computed at start-up, not at build.** The manifest is computed from the embedded files (`go:embed`) when the reader handler is built (once per process; about 1 MB to hash). The embedded content is fixed in the binary, so the versions are as stable as a build-time manifest without adding a generated file or a build step; templates call `{{asset "name"}}`. A missing reader or rendering file fails start-up; KaTeX absent from a checkout where `scripts/copy-katex.mjs` has not run (Go tests only; CI and the image copy it) falls back to the unversioned `/static/` URL, which answers `404` as before.
- **Headers.** `Cache-Control: public, max-age=31536000, immutable`, an explicit `Content-Type` per extension (Go's table has no font types and the distroless image has no `mime.types`), `ETag` from the file's SHA-256, `nosniff`, and **no `Vary: Cookie`**: the route is mounted without the session middleware, so the cookie is never read and never cleared (`Set-Cookie`), and the response cannot depend on it. The server-wide CSP (`default-src 'none'`) applies to these responses; the pages' CSP (`'self'`) already allows them, checked by the browser tests.
- **Old and unknown versions: 404, not a redirect.** Only the current version of each name is served. A redirect to the current version would make an old URL silently serve different content under a long-lived cache, and a CDN could store the redirect. The `404` carries the server-wide `no-store`. Pages are never stored, so only a tab opened before a deployment can hold old URLs; reloading fixes it.
- **Unversioned `/static/` stays, uncached.** It keeps `private, no-store` and its session rules (the fixture image needs a session). It is still used by the loopback renderer experiment's page (left untouched), by the Studio development server (which proxies `/static`) and as the preview's fallback. Removing it can follow once nothing names it.
- **Studio.** Vite already fingerprints the bundle (`assets/<name>-<hash>.<ext>`). Those files, and only names of that shape (a hash of at least 8 URL-safe characters; a Go test checks every file of a built `dist/assets` matches), are now `private, max-age=31536000, immutable`; `index.html`, client routes, error pages and every `404` stay `private, no-store`. The session and Studio-access requirement is kept for the files as well as the shell (the bundle reveals no data, but keeping it staff-only costs nothing and avoids exposing the editor's code paths), so **they are browser-cache only and must never be cached at the edge**. A file left in a browser cache after access is revoked reveals nothing; the next shell request is refused. The Studio preview used to load KaTeX from the uncached `/static/`: the server now adds `<meta name="learnoo-katex-css|js">` with the fingerprinted URLs to `index.html` (escaped, same-origin paths only on the client), so the preview reuses the reader's cached KaTeX; without them (development server) it falls back to `/static/`.
- **Tests.** Manifest unit tests (versions, directory digest, a KaTeX change changing only KaTeX's version, content types, exclusions, missing files); handler tests for headers, `HEAD`, `304`, and `404` for old, other-name, upper-case, truncated and malformed versions and non-public names; server tests that pages reference only fingerprinted URLs, that each asset is byte-identical for signed-out, two students and a forged cookie with no `Set-Cookie`, that KaTeX's relative font URLs resolve, and that pages, the session API, lesson media, the preview and the unversioned files stay `no-store` for signed-out and two different students (each dashboard showing only its own student); Studio tests for the immutable bundle files and `no-store` everywhere else; and a Playwright check (`tests/browser-reader/caching.spec.mjs`, Chromium DevTools protocol) that a second lesson and a second Studio load take every already-loaded fingerprinted asset from the browser cache while the pages are fetched again, with no CSP violation and KaTeX fonts loaded. ## Curriculum (LMS-B02)

Issue #92 implements [LMS_CONTRACT.md §3](LMS_CONTRACT.md#3-curriculum-b02-migration-0013) in `migrations/0013_curriculum.sql`, `internal/curriculum` and the [curriculum API](API.md#curriculum-lms-b02). No curriculum data is seeded; tests use TEST fixtures only.

- **Data model.** `education_levels` (code unique), `academic_sections` (level, code unique per level), `curriculum_editions` (section, code unique per section, `label_fr`/`label_ar`, `state`, `current_since`, `superseded_at`, `retired_at`), `curriculum_assignments` (edition, subject; unique per edition and `(id, subject_id)` as a foreign-key target), `curriculum_assignment_chapters` (assignment, subject, chapter, position; composite foreign keys keep the chapter in the assignment's subject; unique chapter and position per assignment), `retired_at` on `subjects` and `chapters`, and the append-only `curriculum_audit`. Levels, sections and editions also carry `version` and `created_at`; names and labels are required in French and Arabic. The upgrade changes no existing row: every subject and chapter keeps its ID, code, names and order, nothing is retired and no chapter is placed into an edition.
- **Names.** Names and labels reuse `catalogue_valid_name` (0012) and are trimmed in Go with `catalogue.NormalizeName`, like the catalogue's display names.
- **Identities persist.** Levels, sections and editions are never deleted or truncated and their codes and parents never change. Assignments and chapter-list rows are deleted only while their edition is a draft and are never updated. Retirement is one-way, set once to the transaction time, on all five kinds of entries.
- **Edition states.** `draft → current → superseded → retired`, and `current → retired`; never back to draft. A partial unique index allows one current edition per section, and a deferred check lets an edition become superseded only in the transaction that makes another edition of its section current. Each of `current_since`, `superseded_at` and `retired_at` is stamped by its own transition only, and `superseded_at` is set exactly on editions that were superseded (CHECK and guard). At commit, an edition made current must have superseded its predecessor: retiring the previous current edition in the same transaction is refused. Retiring a draft is refused (the contract lists only current and superseded editions as retirable); an abandoned draft stays a draft.
- **Draft-only assignments.** The guards on assignments and chapter lists lock the edition `FOR SHARE` (as `revision_media` does for its revision), which conflicts with the `FOR UPDATE` that make-current and retire take, so an edit cannot commit after the edition leaves draft. They also refuse a retired subject or chapter on insert. The store pre-checks the same rules and answers `409 edition_not_draft` or `422 placement_invalid`.
- **Retired entries cannot be newly selected.** Besides the curriculum tables, the database refuses a chapter added to a retired subject, a new lesson (or translation) in a retired subject, a draft created, saved with a chapter change, or submitted with a retired chapter unless it is the chapter of its base revision (a save that leaves the chapter unchanged is allowed, so the author can still edit or clear it), and a new reviewer grant on a retired subject (re-granting an existing one stays a no-op; revocation works). `internal/catalogue`, `internal/lessons` and `internal/permissions` report these as `ErrSubjectRetired`, `ErrRetiredSubject`/`ErrRetiredChapter` and `ErrRetiredSubject`; the Studio catalogue endpoints expose `retiredAt`. Making an edition current is refused while one of its assignments names a retired subject or chapter (`422 placement_invalid`, naming them; guard too), with the subjects and chapters share-locked after the edition.
- **Make-current.** Lock order (contract §2): permission and account rows (`permissions.Authorize`), then the section's current edition and the target `FOR UPDATE` in ascending ID, then the section and level `FOR SHARE`. The request names the edition it expects to supersede (`expectedCurrentEditionId`, or null); anything else is `409 state_conflict`, so of two racing requests made from the same view one wins and the other changes nothing (a contract ambiguity resolved here: without it two sequential requests would both succeed and the second would silently supersede the first).
- **Optimistic versions.** Every update of a level, section or edition increments `version` by exactly one (guard). Writes name the expected version; assignment and chapter-list edits increment the edition's version, so concurrent edits of one draft conflict instead of overwriting each other. Chapter lists are replaced as a whole (`set_chapters`), one audit row per replacement.
- **Audit, to the standard of the 0012 catalogue renames.** `curriculum_audit` rows name exactly one of `actor_id` or `operator_label`, a target (`level`, `section`, `edition`, `assignment`, `subject`, `chapter`) and ID, the edition for edition and assignment rows, an action and before/after JSON of a fixed shape per action. (1) On insert the row records its own transaction and time, locks the entry until the transaction ends and must carry the entry's current values as `before`; an assignment row's `edition_id` must be the assignment's edition, and `add_assignment` records its subject. (2) Every change of names, labels, order, retirement or edition state needs the latest row of that kind for the entry, in the same transaction, to record exactly that change, so two changes need two rows; inserts and deletes need a row of the matching action at commit. (3) At commit every row was applied: the next row of its kind continues from its `after` values or the entry still has them (a retirement row needs `retired_at` set; an assignment row needs the assignment still in its edition, or removed later in the transaction). The store therefore writes each audit row before its change. Rows are append-only.
- **Selection rule.** `curriculum_assignment_selectable(assignment_id)` is true while the edition is current and neither its section, its level nor its subject is retired. B03 builds placement validity on it. It has a SQL-standard body, so its tables are bound at creation and neither `search_path` nor a caller's temporary table can redirect them.
- **Permissions.** Reads are open to staff (author, publisher, administrator, reviewer of any subject); writes need administrator, checked by the middleware and again in the transaction. The store also accepts an operator actor, audited with its label, for future bootstrap commands; no operator command was added in this slice, because the administrator API covers bootstrap once `bootstrap-admin` has created an administrator.
- **On top of 0012.** The migration follows 0011 and 0012: it adds `retired_at` to `subjects` and `chapters` and guards on `lessons`, `lesson_revisions` and `reviewer_assignments`, reuses `catalogue_valid_name`, and does not touch `catalogue_audit`.
- **Lists.** Level, section and edition lists that exceed 1000 entries are an error, never silently truncated.
- **Not included.** Course placement (B03), discovery and listing of standalone lessons by edition (B07), Studio administration pages (B05/B06), and listing of affected courses on retirement (no courses exist yet).

## Reference reverse proxy (issue 87)

Implementer choices on 2026-11-26 for a reference configuration, tested locally only ([DEPLOYMENT.md](DEPLOYMENT.md#reference-reverse-proxy)). Nothing is deployed; real certificates, DNS, Cloudflare and the shared-server rehearsal stay operational gates on issue 10.

- **Caddy rather than nginx.** Caddy `2.11.3-alpine`, pinned by version and digest, as the Compose override `deploy/compose.proxy.yaml` with `deploy/proxy/Caddyfile`. Automatic HTTPS gives the HTTP→HTTPS redirect and certificate management in a few lines, `tls internal` gives a local certificate for testing, and by default it replaces a client-supplied `X-Forwarded-For` with the connecting address, which is exactly the single hop `LEARNOO_TRUSTED_PROXIES` expects. Stock Caddy has no response cache, so it cannot store a protected response.
- **Trust one address.** The override pins the `frontend` subnet (with a dynamic range that excludes the proxy), gives the proxy a fixed address, removes the app's published port (`ports: !reset []`, Compose 2.24+) and sets the app's `LEARNOO_TRUSTED_PROXIES` to that `/32` in `X-Forwarded-For` mode. This is the option the runbook preferred in issue 46: no host process can reach the app from a trusted gateway.
- **Probes** answer 404 at the proxy for every path under `/healthz` and `/readyz` (decoded, case-insensitive matching); the container health check runs inside the app container.
- **Limits.** Body 6 MiB (5 MiB upload plus headroom), refused up front when `Content-Length` declares more; streamed bodies reach the app, whose own lower limits answer first. Proxy timeouts: read header 10 s, read body 60 s, write 90 s, idle 2 min, upstream dial 5 s and response header 60 s (reference values, not measured on the server). The proxy's read-body timeout is not the binding one: the app's 15 s `ReadTimeout` covers the whole request, so with streaming a 5 MiB upload must arrive at about 3 Mbit/s or gets `408 upload_timeout`.
- **Headers.** The proxy adds HSTS (`max-age` configurable, default 31536000 as an EXAMPLE; no `includeSubDomains` or `preload`, which belong to the domain owner) and removes `Server` and `Via`. It never overrides the app's headers; it only fills the app's strict defaults (`no-store`, `nosniff`, `DENY`, `same-origin`, `default-src 'none'`) on responses the app did not produce, including errors Caddy raises itself (`handle_errors`: `502`, a streamed `413`), whose body is just the status code.
- **Caching.** The proxy caches nothing. Shared caching is allowed only for responses the app marks `public`, i.e. the fingerprinted `/assets/<version>/<name>` files ([Fingerprinted static assets](#fingerprinted-static-assets-issue-88)), the only edge-cacheable prefix; everything else, including `/static/` and `/studio/assets/` (`private`), bypasses proxy and edge caches. The proxy states the rule by `Cache-Control`, not by hard-coded paths, and never rewrites `Cache-Control`.
- **Access log.** JSON on stdout. The raw request target is filtered case-insensitively: `/invite/<token>` → `/invite/REDACTED`, any other path naming `invite` or containing a percent-escape → `REDACTED` (non-canonical spellings such as `//invite/`, `/./invite/` and `/%69nvite/` reach or name the invitation route; redacting every percent-escaped path is broader than needed but cannot miss an encoding), query strings → `?REDACTED`; credential, cookie, Referer, CSRF and Location headers are dropped, in the access and error logs. This adds the request log that LRN-010 left to the proxy; the app still has none.
- **Non-root.** Caddy runs as uid/gid 65532 on ports 8080/8443 inside the container (published as the host's 80/443 on a server); the HTTP site redirects explicitly to the default https port because Caddy's automatic redirect would name 8443. `NET_BIND_SERVICE` stays the only capability, unused, because the image's binary carries it as a file capability and cannot be executed without it in the bounding set; stripping it needs a derived image, not done here.
- **Test.** `deploy/proxy/test-proxy.sh` runs the stack in an isolated Compose project with throwaway secrets and checks redirect, headers (including on probe 404s, `413` and `502`), probes, body limits, two users plus signed-out without proxy caching, `/assets/` public and `/static/`, `/studio/assets/` private through the proxy, the throttle keyed on the real client (two client containers with fixed addresses, forged `X-Forwarded-For` ignored) and log redaction with non-canonical invitation paths, then removes everything it created. It is not run in CI (it needs Docker and builds the image).
- **Left open** (infrastructure maintainer): the domain, certificate source, published addresses, HSTS value and preload, the subnet, whether Cloudflare is used and with which client-address header and origin lockdown, and whether the shared server's existing proxy (if any) is used instead of this one. **Open decision: slow uploads.** Whether slow connections need request buffering at the proxy (`request_buffers`, so the app receives the body at once) or a longer app read timeout; until decided, uploads slower than about 3 Mbit/s for 5 MiB fail with `408 upload_timeout`. Behaviour is unchanged.

## Courses (LMS-B03)

Issue #93 implements the draft side of [LMS_CONTRACT.md §4 and §5](LMS_CONTRACT.md#4-courses-b03-migration-0014) in `migrations/0014_courses.sql`, `internal/courses` and the [course draft API](API.md#course-drafts-lms-b03). Tests use TEST fixtures only.

- **Data model.** `courses`, `course_revisions`, `course_revision_assignments`, `course_modules` and `course_steps` with the contract's columns and composite keys: every child row carries its revision's subject (and language for modules and steps), a module's chapter is in that subject, a step's lesson is in that subject and language and its pinned revision belongs to that lesson. A step has its own course-authored title. The columns B04 needs (`published_revision_id`, `archived_at`, `dependency_count`, `submitted_at`, `candidate_closed_at`, `withdrawn_at`, `kind`, `compare_revision_id`) exist now; every change B04 will make is refused until B04 replaces or drops the guard concerned (the `courses` update guard admits only `last_revision_number` growth; `zz_guard_course_revisions_not_submittable` refuses any status change; `candidate_closed_at` and `withdrawn_at` change only from an owner-run trigger, as in 0004).
- **Revisions mirror lessons.** Created as a draft at version 1 at the transaction time; `base_revision_id` and `compare_revision_id` equal the course's published pointer (B04 adds the audit fallback of §5 to the comparison); identity columns never change; every draft update increments `version` by one; only drafts are deleted; revision numbers are never reused (`last_revision_number` only grows, and only to the highest revision number of the course, which is what the insert trigger sets). One active candidate per course: the 0004 predicate, excluding withdrawn revisions.
- **Ownership and cover.** On insert and every draft update the author equals the course's owner (course locked `FOR SHARE`). The cover is an image the author uploaded (`media_uploads`), with `cover_alt` required with it and absent without it.
- **Draft-only children.** Placements, modules and steps change only while their revision is a draft (guard locks the revision `FOR SHARE`, like `revision_media`; for steps `FOR UPDATE`, so concurrent step inserts into one draft serialize). A placement names only an assignment of an edition that left draft, since a draft edition's assignments can still be removed or changed. The step guard counts steps on insert and when a step moves to another revision (at most 200; exact at `READ COMMITTED`, where the count re-reads after the lock); module positions are 1 to 50 and unique, which bounds modules.
- **Attachability in the database.** The step guard, on insert and on any change of a step's lesson, pinned revision or revision, share-locks the lesson and the course and refuses a lesson whose `created_by` is not the course owner unless `course_step_revision_eligible` holds. A direct writer therefore cannot pin another author's draft (which would block that author's discard) or any non-eligible revision of another author's lesson.
- **Delete.** A course is deleted (cascading to its drafts and their children, never lessons or media) only while none of its revisions left draft and it was never published. A submitted revision never returns to draft and is never deleted, so its existence is the history.
- **Shared definitions.** `course_step_revision_eligible(lesson_id, revision_id)` (§5) and `course_revision_placement_problems(rev_id, check_mode)` / `course_revision_placement_valid(rev_id, check_mode)` (§3) have SQL-standard bodies (tables bound at creation). The mode is `save`, `submit` or `publish`; B04 calls the last two. In save mode an assignment not on the comparison revision must be selectable (`curriculum_assignment_selectable`) and one carried from it may be superseded or (flagged, not refused) retired; submit additionally refuses a carried retired assignment and no assignment at all; publish accepts current and superseded editions only. Amendments must keep the comparison's assignments, whatever their state. Every mode requires each module chapter to be in one of the revision's assignments and not retired unless inherited unchanged (same module key and chapter on the comparison revision).
- **Attach rules (store).** Own lessons (any revision, drafts included) or another author's lesson that is currently published (eligible revision only); same subject and language; a lesson once per revision. Another author's unpublished lesson is reported like a missing one. The save re-validates every step. Draft creation copies only the steps still attachable and lists the others (`droppedSteps`), since the step guard refuses them.
- **Lock order** (§2): permission rows, then the editions of the requested assignments, then (save) their sections, levels and subjects and the requested module chapters, so a concurrent retirement (which takes the entry `FOR NO KEY UPDATE`) either waits for the save or is seen by the save's placement check, then the lessons and the pinned lesson revisions (all `FOR SHARE`, ascending ID), then the course (`FOR SHARE` for save and discard, `FOR UPDATE` for draft creation and delete), then the revision `FOR UPDATE`. Locking the pinned lesson revisions before the course is an addition to §2: a lesson draft discard locks the lesson, then its revision `FOR UPDATE`, so a course save holding the step rows could otherwise wait for it in the opposite order. A lesson draft pinned by a course draft is refused by the lesson discard path with `409 referenced_by_course` (checked under the lesson revision lock; the foreign key backs it up).
- **Contract ambiguities resolved.** (1) Draft creation copies the course's latest revision (so corrections after `changes_requested` start from the reviewed structure) rather than taking a body; the copy is not validated until the next save. (2) `kind` is always `ordinary` in B03 (amendments need a published comparison, B04). (3) Drafts may leave overview fields empty; B04's submission decides what is required (`422 incomplete`). (4) Module and step titles are required (1 to 200) since they are reviewed structure. (5) The cover error is the existing `422 unknown_media`, identical for a missing asset and another user's. (6) `GET /api/lessons/{id}/eligible-revisions` lists every revision of the caller's own lesson with an `eligible` flag, since a draft step may pin any of them. (7) "Flagged on save" for a retired carried assignment is the `retired` field of the placement in the response. (8) The owner's course list pages by course ID, newest first, 100 per page, with a cursor.
- **For B04.** The draft-update rules mirror 0004. Course submission must compare `expectedVersion` in its `UPDATE` and leave the content unchanged (only status, `submitted_at`, `updated_at` and `version`), as lesson submission does; amendment creation must lock the course `FOR UPDATE`, like draft creation, so it serializes with other draft creation and with the active-candidate check. Race tests cover a save racing a withdrawal and an unpublication of a pinned foreign lesson, and MakeCurrent and RetireEdition of a requested assignment's edition.
- **Not included.** Submission and its audit, review, publication, suspension, archive, withdrawal, transfer, amendments, dependency events, newer-revision notices (B04), Studio pages (B05/B06) and reader routes (B07/B08).
